# `proscenium_sync.runtime`

The bindings' runtime: lookups and writes on their records, read when called, and every binding's stages ([Undo and Runtime State](../../../../../docs/spec/lifecycle.md#undo-and-runtime-state), DECISIONS.md "Binding records read when called").

Code in other units reaches it through the modules `__init__.py` exports ([import rules](../README.md#import-rules)); tests reach into any module.

| File | Holds |
|---|---|
| `__init__.py` | The package's exports: its modules. |
| `copy_detection.py` | Copied-binding detection ([Copied Bindings](../../../../../docs/spec/source-access.md#copied-bindings)): `BindingRecord`, one collection's binding record as read; `candidates_for_binding()` and `candidates_by_binding()`, which read an identity's candidates, its binding records that can't be read or name a target scene that exists, and return them (`IdentityCandidates`) with the decision of the rule in `proscenium_sync.source_access.canonical_candidate`; and `copied_binding_report()`'s `CopiedBinding`. |
| `binding_operations.py` | Lookups by binding identity (`find_binding`, `find_bindings`), which reach the canonical candidate's binding record and return a `FoundBinding`, with its destination and target scene: usable with its configuration, unreadable with why, or disabled with its copies; binding creation; configuration writes; and restoring a missing index entry after a write. |
| `ownership.py` | Ownership: `of(datablock)`, an `Ownership` whose `status` says whether the datablock is unmanaged, managed, or ambiguous, from the `Claim`s on it in the manifests among its users (`bpy.data.user_map`). Also a binding's manifest (`manifest`), and manifest writes, whole (`set_manifest`) or by entry (`set_manifest_entries`, from the manifest its caller read, if given). |
| `pending_cleanup.py` | The pending-cleanup ledger (`ledger`), read from the index's Text, its writes by entry (`set_ledger_entries`), whether it can record a failed removal (`check_trackable`), and a binding's current cleanup diagnostics, which every result reports as its cleanup status (`cleanup_status`), and whether a binding has none of its entries (`nothing_pending`). A file with more than one binding index refuses the ledger and its writes, and reports an empty status. |
| `copy_partitions.py` | `PublishedPartitions`, a published manifest's copies' partitions by source entity, each a `CopyPartition`: its entries, and whether a resource of it is gone, it has a shear parent, a second object, an action keying cached time codes, or an entry using a shared datablock; and the shared datablocks' entries only some entries use (`unused_shared`). Built from a whole manifest, it takes a write by entry's changed and removed entries in place (`replace_entries`), grouping again only the copies they cover. |
| `kept_manifests.py` | Manifests kept between operations by their stored revision, which each record write renews: `read_manifest` returns a destination's kept manifest while its revision is the stored one and every datablock it names is alive, and decodes it otherwise; `write_manifest`, `write_manifest_entries`, and `remove_manifest` write through `proscenium_sync.persistence.manifests` and keep what they wrote; `clear`, which `registration.py`'s handlers call after a file load, an undo, and a redo. Beside a kept manifest, `published_partitions` keeps its copies' partitions (`copy_partitions`), built when first asked for and given each write by entry's changed and removed entries. Every manifest read and write goes through it. |
| `held_plans.py` | `HeldPlans`: the plan of each generation this session published for a binding, by its generation record without cached time codes (`generation_key`), a bounded number per binding, oldest dropped first, for a refresh to compare against the generation the destination shows (DECISIONS.md "Incremental refresh comparison"). |
| `stage_tracking.py` | `BindingStageTracker`: every binding's stages, in source access's `StageRegistry`, compared with the bindings that exist before each use. Vanished bindings keep their attachments and drop their evaluation stages; unreadable and disabled bindings retain both. |

## Records read when called

- **Every lookup reads the records** as they are when it's called, a manifest from its kept copy while the stored revision is the one it was kept at, and every write writes them, so no lookup can return a removed datablock: Blender clears a removed datablock's pointers in the records, and a kept manifest's datablocks are checked alive before it's returned.
- **The stages, the held plans, and the kept manifests are runtime state,** with the chain each binding's stages keep over its evaluation stage. A manifest is kept by its stored revision, so a manifest changed other than by a write, as by a script editing its ID properties, is seen after the next write, undo, redo, or load (DECISIONS.md "Binding records read when called"). `registration.py`'s handlers release the stages and clear the held plans when a file is loaded, prune the stages after undo and redo, and clear the kept manifests after each. Undo and redo leave the held plans: they're found by the generation record the destination holds, which undo restores with the display.
