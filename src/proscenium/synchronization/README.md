# `proscenium.synchronization`

The synchronization transaction ([Synchronization Transaction](../../../docs/spec/pipeline.md#synchronization-transaction)): one attempt to display a binding's source, from acquisition through retirement; the cache call, which caches time codes in the published generation ([Cached Time Codes](../../../docs/spec/pipeline.md#cached-time-codes)); and the application layer they apply display plans with. Tier 4: `proscenium.api` calls it, and it may import every unit below it ([import rules](../README.md#import-rules)). M5's application layer is a stub, which M7 replaces.

| File | Holds |
|---|---|
| `__init__.py` | The package's exports: `transaction`, `caching`, and `cleanup_retry`. Evaluation, the application layer, prepared work, publication, retirement, and removal are theirs. |
| `application.py` | M5's stub application layer, which M7 replaces: `prepare` makes each of a plan's drawn copies, an object drawing its bounds and its bounds mesh, under an unselectable shear parent when the plan splits its world transform, in prepared work's staging collection, which no scene links, keyed by the published entries whose identities they have, and tracks each as it's made. Preparation only creates datablocks, so it changes nothing the published generation reaches (TXN-05). `key_time_codes` keys the published copies' transforms at a cache call's time codes, constant until the next key, in an action per object, made and tracked when the object is first keyed, which is keyed at the generation's own time code too, holding how to undo each change in the prepared work before making it; it returns the manifest changes, each new action's entry and its object's using it. Also the representation version it applies, which the planning context names. |
| `caching.py` | `cache`, a cache call for a binding the caller has found usable: it evaluates and plans the source at each time code the published generation hasn't cached, under the generation's payload policy, before changing any Blender data, then has the application layer key them, adds its actions to the manifest by entry, and adds the time codes to the generation record. It publishes no generation and records no last attempt. A generation at the default time code has nothing to cache, so the call succeeds (CACHE-06); one with no generation, or whose source revision differs from the generation's, which it checks even with nothing new to cache, fails with a `needs-synchronization` diagnostic (CACHE-05). A call that fails caches none of its time codes: it reverts its keys and the manifest and disposes of its actions, each whose removal fails entering the ledger (CACHE-03). |
| `cleanup_retry.py` | `retry_cleanup`, the explicit retry of a binding's pending cleanup, without USD access: its leftovers are removed through `removal.remove_unused`, the ledger's Text aside, and one that still can't be removed stays retryable with a fresh diagnostic. Resolved entries leave the ledger with their diagnostics, and a ledger that can't be read refuses. |
| `evaluation.py` | What the transaction and a cache call share before changing Blender data: `source_state`, the dirty-layer diagnostic a display reports, and `plans`, the plan at each of some time codes, captured within `BindingStages.changed_layers()` so a layer changing meanwhile discards them (CONS-03), or the fatal diagnostic saying why there are none. |
| `prepared_work.py` | `PreparedWork`, what a preparation has made, which the stub and M7's application layer share: `untrackable` says why none can be made when the ledger couldn't record a failed disposal; `track` holds each resource before anything else can fail (TXN-08), `undo` how to undo each change a cache call makes to a published resource, which `revert` runs in reverse, and `dispose` removes it all through `removal.remove_unused`, the staging collection aside, recording in the pending-cleanup ledger only each removal that fails, retryable, with its cleanup diagnostic; after publication, `remove_staging` lets go of it. |
| `publication.py` | `publish`, the switch to prepared work: the destination's links, the manifest written whole, and the generation record, each undone in reverse when a later one fails, so the published generation is all old or all new (TXN-06); it returns the obsolete resources for retirement. |
| `transaction.py` | `synchronize`, the transaction's steps for a binding the caller has found usable: it refuses one whose records it needs can't be read, then acquires, evaluates and plans through `evaluation` (discarding the attempt if a contributing layer changes meanwhile), prepares, and publishes, each failure before publication a fatal diagnostic with prepared work disposed of and each disposal that failed reported, and retires, a ledger write that fails raising as a defect, and records the last attempt on every outcome (STATE-03). It pushes no undo step; `Bindings` does. |
| `removal.py` | `remove_unused`, the removal disposal, retirement, and a cleanup retry share: from each datablock's users, read once, it removes those nothing else uses a level at a time, users first, releases intact those something else uses, and leaves pending, with why, those whose removal or whose user's failed (`RemovalOutcome`). Each level goes through `remove`, one `bpy.data.batch_remove` call, since each call scans the file, and only when it raises is it halved until each that fails is alone, never passing one already removed, on which Blender crashes. |
| `retirement.py` | `retire`, which removes the obsolete resources publication returned through `removal.remove_unused`. Only one whose removal fails, or whose user's did, enters the ledger, retryable with its cleanup diagnostic, and the synchronization completes with issues (TXN-07); one anything else uses is released intact. |
