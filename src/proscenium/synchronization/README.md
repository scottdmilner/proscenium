# `proscenium.synchronization`

The synchronization transaction ([Synchronization Transaction](../../../docs/spec/pipeline.md#synchronization-transaction)): one attempt to display a binding's source, from acquisition through retirement, and the application layer it applies display plans with. Tier 4: `proscenium.api` calls it, and it may import every unit below it ([import rules](../README.md#import-rules)). M5's application layer is a stub, which M7 replaces.

| File | Holds |
|---|---|
| `__init__.py` | The package's exports: `transaction` and `cleanup_retry`. The application layer, prepared work, publication, retirement, and removal are theirs. |
| `application.py` | M5's stub application layer, which M7 replaces: `prepare` makes each of a plan's placeholders, an object drawing its bounds and its bounds mesh, in prepared work's staging collection, which no scene links, keyed by the published entries whose identities they have, and tracks each as it's made. Preparation only creates datablocks, so it changes nothing the published generation reaches (TXN-05). Also the representation version it applies, which the planning context names. |
| `cleanup_retry.py` | `retry_cleanup`, the explicit retry of a binding's pending cleanup, without USD access: each leftover whose only users are the ledger and other leftovers removed before it is removed, a level at a time; one anything else uses is released intact; one that still can't be removed stays retryable with a fresh diagnostic. Resolved entries leave the ledger with their diagnostics, and a ledger that can't be read refuses. |
| `prepared_work.py` | `PreparedWork`, what a preparation has made, which the stub and M7's application layer share: `track` holds each resource before anything else can fail (TXN-08), and `dispose` removes it all, recording in the pending-cleanup ledger only each removal that fails, retryable, with its cleanup diagnostic; after publication, `remove_staging` lets go of it. |
| `publication.py` | `publish`, the switch to prepared work: the destination's links, the manifest written whole, and the generation record, each undone in reverse when a later one fails, so the published generation is all old or all new (TXN-06); it returns the obsolete resources for retirement. |
| `transaction.py` | `synchronize`, the transaction's steps for a binding the caller has found usable: it refuses one whose records it needs can't be read, then acquires, evaluates (discarding the attempt if a contributing layer changes meanwhile), plans, prepares, and publishes, each failure before publication a fatal diagnostic with prepared work disposed of and each disposal that failed reported, a ledger write failing in disposal or retirement reported too, never raised, and retires, and records the last attempt on every outcome (STATE-03). It pushes no undo step; `Bindings` does. |
| `removal.py` | `remove`, which removes datablocks in one `bpy.data.batch_remove` call, since each call scans the file, and only when it raises removes the rest one call each to find which fail, never passing one already removed, on which Blender crashes. Disposal and retirement remove through it. |
| `retirement.py` | `retire`, which removes the obsolete resources publication returned, in levels by the old manifest's uses, users first, each level in one call unless one fails. Only one whose removal fails, or whose user's did, enters the ledger, retryable with its cleanup diagnostic, and the synchronization completes with issues (TXN-07); one anything else uses is released intact. |
