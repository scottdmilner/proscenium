# M3 — Binding model, source access, identity, and persistence schemas: plan

How M3 will settle its contracts and deliver tested source access, the binding model, and versioned persistence schemas, and the order of work. Requirements are in the [M3 milestone](../milestones/M03-bindings.md); where this plan and a requirement file disagree, the requirement file wins. Mechanisms named here are suggestions unless marked settled. Each phase gains a short decision log once work starts, in the style of the [M2 plan](M02-contracts.md).

M3 is the first milestone that ships product code. It delivers the matrix rows whose `delivery` is M3: the Bindings and Source Access rows (BIND-02 to BIND-10), API-01 to API-03, API-06, CONS-03, SID-03 to SID-07, COPY-01 to COPY-04, the In-Memory Sources rows (MEM-01, MEM-02, and MEM-04 to MEM-08), the File-Backed Refresh rows (FILE-01 to FILE-07), OWN-01, UNDO-06, UNDO-07, STATE-01, the Reopening rows (REOPEN-01, -02, -04, -05, -07), the Schema Versions rows (SCHEMA-02 to SCHEMA-05), ICON-07, ICON-24, and AFIX-04.

## Settled with the user (2026-10-15 to 2026-10-18)

- **One kind of binding (2026-10-18).** Every binding has a source stage, the stage its source is composed on, which is also its live stage ([live inspection](../spec/interaction-contract.md#two-layers-and-the-live-stage)). Its source is a file source, whose source stage the binding opens itself, or an attached source, whose source stage a caller attaches under a source key. One rule set covers both: an evaluation stage that composes the source stage's root and session layers, matching its mask, muting, and interpolation, under the binding's own payload policy, which is the source stage itself when the binding opened it.
- **A binding with a file source reuses its own source stage.** The binding opens one stage outside every USD stage cache (`Usd.BlockStageCaches`), keeps it, and reuses it across refreshes. It is never shared with another binding or tool, and refresh doesn't reopen it, so the binding's Hydra chain can also persist across refreshes for Phase 2. A first synchronization, including the first after reopening a `.blend`, opens the stage.
- **The source stage's anonymous layers are displayed.** A refresh shows the source's layers composed with the opinions in the source stage's session layer and the anonymous layers beneath it, so a future editor can show unsaved edits through the live stage without saving and reopening. Synchronization never authors them, a reload never rereads them, and they are not saved in the `.blend`.
- **Layers are displayed as loaded, and reloaded only on request (2026-10-18).** Both kinds of binding display their source's layers as loaded in the process, dirty ones included, with an informational diagnostic naming the dirty layers. Synchronization never reloads. `handle.reload(layers=None)` rereads the binding's contributing layers (the non-anonymous layers its stage uses under its payload policy), or only the named ones; a dirty layer is reloaded too, discarding its edits, and saving them first is the caller's responsibility.
- **Source acquisition is Python `pxr`:** opening the source stage, the evaluation stage, reloads, and runtime attachments. Every API it needs is in Python `pxr`, and Python stays the preference outside the core. The core receives a stage, takes its own reference, and releases it explicitly; it never keeps a released stage alive.
- **Persistent state is versioned ID-property records:** namespaced nested ID-property dicts on the Scene (binding records, persistent selection) and on managed IDs (ownership tags), each with a `schema_version`. Python schema code reads, migrates, and validates them, so records stay readable without registered RNA.
- **Source key contract:**
  - The key is a caller-chosen string that names one attached source within a `.blend`. Several bindings may share it, and attaching a stage under a key attaches it to all of them (2026-10-16).
  - Reattachment requires an exact key match.
  - The root-layer identifier is informative: it is never used to find bindings.
  - Replacing the attached stage preserves stored source selections; they resolve against the next published generation.
  - Attaching a stage whose root-layer identifier differs from the stored one requires explicit confirmation from the caller.
- **Copied bindings (with the user, 2026-10-19).** Phase D probed what Blender does to ID properties and ID pointers on each copy route (D1). The canonical candidate is the one a file-level binding index names, when its binding record and destination refer to each other. Without a usable index entry, it is the one candidate whose record and destination refer to each other. Otherwise all candidates are disabled pending repair. Linked bindings are not candidates.

## Phases

Each phase ends with a review by the user before the next starts. Each phase lists its commits in order. Every commit is one feature and passes `pre-commit` and the test suite on its own:

- A spec change lands with its matrix rows, its `invariants.md` bullet, and its DECISIONS.md row.
- A new fixture lands with its registry entry, its Named Contract Fixtures row, its mention in the M3 Tests section, and a row that uses it.
- Code lands with its tests.
- A decision lands with its line in the phase's decision log.

If a commit grows past one feature, it splits, and this list is updated in the same commit.

### Phase B — Compiled core bring-up

- **B1, shared build code.** `tools/blender_deps.py` (the pins and the dependency checkout) and `tools/native_build.py` (toolsets, the CMake build, and the linkage audit) come from the bridge's `prepare_deps.py` and `build.py`. - **B2, the core in the extension build.** The module is `proscenium.core._core`, with one function, `usd_version()`, so tests can check it was built against the host's USD. `build_extension.py` builds it into `src/proscenium/core/` (ignored by that directory's `.gitignore`), the way it syncs `wheels/`, and skips the build when `build/core/build.json` records this platform, the locked release, and the current hashes of the sources, the build tools, and the module. Only a temporary copy of the manifest gets `platforms` and `blender_version_max`, so the checked-in manifest is the same on every platform and release. Each zip supports only the locked release's minor version (5.2.x): the maximum is the next minor (`5.3.0`, the first unsupported version), and the build fails unless the hand-written `blender_version_min` is in that minor. - **B3, clang-format and clang-tidy.** Both come from PyPI in the dev group, so `uv.lock` pins them like the other hooks. They cover `src/proscenium/core/` only; the bridge is evidence and keeps its own style. The format is Google's with 120 columns. clang-tidy runs the bugprone, clang-analyzer, misc, modernize, and performance checks, without trailing return types (a style choice) and include-cleaner (it can't follow pxr's umbrella headers), and every warning fails. It reads the compile commands of the core's CMake build, which `tools/clang_tidy.py` configures first through `native_build.configure`, so it parses the core with the build's flags and Blender's headers. - **B4, error translation and the stage handle.** The bindings use `pxr_boost::python` (DECISIONS.md row "Python bindings for the compiled core", with the user). Each entry point opens a `TfErrorMark` and raises the Tf errors posted since as `pxr.Tf.ErrorException` (`errors.h`). C++ exceptions use pxr_boost::python's own translation (`std::invalid_argument` is `ValueError`, any other `std::exception` is `RuntimeError`), so the core adds no translator. `_core.StageHandle(stage)` takes a weak stage pointer and adds its own reference, since Tf's converter for a `TfRefPtr` argument moves ownership out of the caller's Python object (M1b Phase C). `release()` drops that reference; `stage()` then returns the stage only while someone else holds it. `proscenium.core` imports `pxr.Usd`, not only `pxr.Tf`: the core's stage arguments need pxr.Usd's Python converters, which a process with bpy may not have registered either. `_core.pyi` gives the module's types, so ty checks callers where it isn't built. Tests: in `isolated/`, a stage the caller dropped stays alive while held and expires after `release()`, which is the core's part of MEM-05, and releasing a handle leaves a caller-held stage alive. In `bpy_free/`, a posted Tf error and a C++ exception each raise their Python exception.
- **Source-entity identifiers (with the user, 2026-10-17).** A source entity's identifier is its prim path in the composed stage: the instance-proxy path inside native-instance contents, which carries its instance context, as M2's oracle names entities. It is never a Hydra-generated path or an instancer index, and is persisted as the path string. The instance context and the floor are computed from a stage when needed, during synchronization or on the live stage, never stored: without a live stage no interaction function runs, and a stored context would go stale when the source's instancing changes, while a path resolves against the next published generation (SID-07). The identifier arrives with its first user, the persistent selection schema (D7); the correspondence layer that derives floors is M4's.

#### Phase C log

- **C1, the contract (with the user).** Every binding has a **source stage**, the stage its source is composed on, which is also its live stage. Its source is a **file source**, whose source stage the binding opens itself outside every stage cache, or an **attached source**, whose source stage a caller attaches under a source key. The binding evaluates an **evaluation stage**, which composes the source stage's root and session layers, matching its mask, muting, and interpolation, under its own payload policy, and never changes the source stage's settings; when the binding opened the source stage, the evaluation stage is the source stage, since a second stage over ALab's loaded layers cost 259–289 ms and 36 MB in three ad hoc runs. What differs by source is only who opens the source stage, when the source is unavailable, and what is saved. Bindings display their source's layers as loaded in the process, unsaved edits included, and synchronization never reloads, so a binding shows work in progress and reloads, whose effects reach every stage sharing the layers, happen only when a caller asks. A reload happens only on request, through `reload(layers=None)` beside `set_settings`: it rereads the contributing layers whose files changed and every dirty one, discarding its edits, or only the named contributing layers; naming any other layer is misuse. Saving edits first is the caller's responsibility. Reloads are non-forced, so unchanged layers send no notices; on Windows, where USD stores whole seconds, a rewrite within the same second as the last read isn't reloaded, as in USD itself. A synchronization that displays dirty layers reports an informational source-state diagnostic, which leaves its result state unchanged (M5 reports it), and the fatal source-access category is an unavailable source. A non-forced reload rereads a dirty layer whose file is unchanged (one check). Spec: [Source Stages](../spec/source-access.md#source-stages) and [Layer State and Reloading](../spec/source-access.md#layer-state-and-reloading) replace In-Memory Sources and File-Backed Refresh. Rows SRC-01 to SRC-08 replace MEM-01, -02, -04 to -08, FILE-04, and FILE-08; LAYER-01 to LAYER-07 replace FILE-01, -02, -03, -05, -06, and -07. The Synchronization API gains `reload` (API-07), the live-stage rows (ICON-07, -32, -33) and lifecycle's Binding State follow the source stage, and DIAG-09 and DIAG-11 follow the diagnostic categories. The `F-DIRTY-LAYER` cases are "as-loaded" and "reload". The DECISIONS.md rows "One kind of binding" and "Dirty layers and reloading" record the decisions.
- **C2, style and tooling.** Classes declare their typed attributes above `__init__`, and every override is marked with `typing.override`; ty's `missing-override-decorator` and `possibly-missing-attribute` rules are errors, and the two existing overrides, in `bpy_blocker.py` and `probe_undo.py`, are marked. `.vscode/` is ignored.
- **C3, the binding source, for file sources.** Source access is the package `proscenium.core.source_access`. A `BindingSource` holds a source and the evaluation stage it keeps and reuses; it isn't named for the source stage it holds, which the spec's term means. A `FileSource` holds a root path and opens its source stage at the first acquisition under `Usd.BlockStageCaches`, never placing it in a cache; a failed open is `SourceUnavailable`, an expected outcome that the synchronization API returns as a result. For a file source the evaluation stage is the source stage, and `live_stage` returns it. The payload policy is USD's own `Usd.Stage.InitialLoadSet`, the initial load set at the open; a change is recorded and applied at the next acquisition with `Usd.Stage.Load()` or `Unload()`, never a reopen, so the session layer's opinions stay. Acquisition displays layers as loaded and reloads nothing. Tests are by spec section, and the rules every binding follows are parametrized over the kinds of source (`tests/bpy_free/bindings.py`). `test_source_stages.py`: the stage kept and reused, the live stage, session-layer opinions, a missing file, the initial payload policy, a policy change, and switching it and back; the `F-CACHED-STAGE` "ambient-cache" case (SRC-01); and two bindings on one file with their own stages. `test_layer_state.py`: the `F-DIRTY-LAYER` "as-loaded" case (LAYER-01), with no notices on a second acquisition. The case's ICON-34 check comes with the binding handle (C8).
- **C4, attached sources.** An `AttachedSource` holds the source key, the root-layer identifier of the stage last attached, which `attach` stores, and a released `_core.StageHandle`, so attaching never keeps the caller's stage alive (SRC-02); a Python weak reference to the `Usd.Stage` returns an expired wrapper when the stage expires while pxr still holds its wrapper (as when a stage cache erases it), which depends on pxr's undocumented wrapper bookkeeping, while the handle's `stage()` reports the C++ stage's expiry directly (one check each). The key and identifier are binding configuration that the binding records (Phase D) persist; until then they are held here. The evaluation stage is opened with `Usd.Stage.OpenMasked` over the attached stage's root and session layer objects, with its resolver context and population mask and the binding's payload policy, under `Usd.BlockStageCaches`; each acquisition then matches its population mask, muted layers (`MuteAndUnmuteLayers`), and interpolation type. It is reused while the attached stage's root and session layers are the same objects, and a new one opens otherwise. `live_stage` is the attached stage. With nothing attached, or the attached stage expired, acquisition raises `SourceUnavailable` and drops the evaluation stage, which holds the caller's layers. Tests: the shared tests now run for both kinds; the `F-PRIVATE-STAGE` "caller-settings" case under each payload policy (SRC-04 to SRC-07), with the settings matched again after the caller changes them between acquisitions; the "payload-policies" case (SRC-08); a caller with another session layer gets a new evaluation stage; with the caller cached and its cache context active, the evaluation stage is still not the caller.
- **C5, reloading on request.** `reload(layers=None)` acquires, then rereads every contributing layer (the non-anonymous layers the evaluation stage uses under its payload policy) in non-forced `Sdf.Layer.ReloadLayers` passes until composition brings in no new layer, since a reload that changes composition can bring in a layer another tool read before its file changed. Not `Usd.Stage.Reload`, which also reloads anonymous layers outside the session layer and discards their content (one check). A forced reload of an unchanged layer notifies every stage using it (info-only changes at `/` and `/World/Var`, one check). With layers, `reload` checks that each identifier is a contributing layer, raising `ValueError` before reloading anything, and rereads only those. `dirty_layers()` lists the dirty contributing layers, for the source-state diagnostic. Tests, for both kinds: the dirty layers under each payload policy; the `F-DIRTY-LAYER` "reload" case (LAYER-03, LAYER-06, LAYER-07), with the metamorphic check against a stage opened on copies of the files with the same session-layer opinions; load-none leaving the payload-only layer (LAYER-04); named layers (LAYER-05); no notices for unchanged layers; a layer brought in by recomposition; and a rewrite within one second, reloaded on macOS and Linux and expected to be missed on Windows, so the test fails if USD's behavior changes. - **C6, the source registry.** `SourceRegistry` maps every binding's identifier to its `BindingSource`, with a file source (`add_file`) or an attached one (`add_attached`), so synchronization looks up either kind the same way. Its cases join once SRC-03 and SID-07, which need the binding records, have tests. Tests: SID-03 to SID-06 and ICON-07 on `F-REATTACH`; a stage over the same root layer reattaches without confirmation; each kind's binding source is found by identifier; and attaching under a file source's binding identifier, with the caller's root layer, leaves it alone. Tests on `F-MULTI-BINDING`: each root-layer format composes the same values (BIND-02); two bindings with the same file source and one with a stage over that file attached have distinct evaluation stages, none the attached stage (BIND-07); payload policies on one file (BIND-04); a default binding composes every prim of the scene, unmasked (BIND-08); acquisitions under both policies dirty and rewrite no layer and compose the authored variant selection (BIND-09); a payload-policy change leaves the other bindings' stages and policies and the caller's load set (BIND-10, for the payload policy). The caller's unsaved root-layer edit shows in a binding with that stage attached, not in the file on disk (BIND-03), and in a binding with that root as its file source, not in one on the `.usdc` root over the same sublayers; a disk change reaches the attached binding and the caller only after a reload; and the caller's muting and session-layer opinions reach its binding, not one with the same file as its source. With the attached binding evaluating the caller's stage itself, three of these fail.
- **C8, the synchronization entry point, acquisition only.** `proscenium.core.synchronization` holds the functions keyed by binding identifier that the spec's design note says tests exercise. A `Synchronization` holds the bindings' `SourceRegistry` and their requested settings (time code and payload policy), runtime state until the binding records exist (Phase D); `SYNCHRONIZATION` is the process's. `create_file_binding` and `create_attached_binding` make a binding with a stand-in identifier (a UUID) and return a `BindingHandle`, a frozen value of the identifier whose methods (`synchronize`, `set_settings`, `reload`, `requested_settings`, `live_stage`) delegate to those functions and raise `BindingNotFound` once the binding is removed. `attach` and `remove` span bindings. `synchronize(time_code)` records the requested time code, applies the requested payload policy, and acquires the evaluation stage; it returns an immutable `Result` of a state and diagnostics. An unavailable source is a fatal-failure result with an unavailable-source diagnostic, as is a `reload` of one; displayed dirty layers give one informational source-state diagnostic naming them, and the state stays success. M5 adds evaluation, planning, application, publication, and the reentrancy guard (API-05); where the handle's lookups go once the records exist is Phase D's. Tests: handle equality, the requested time code recorded exactly for the default, integer, and non-integer time codes (BIND-05), `set_settings` recording without synchronizing, an unavailable file and an unattached binding as results, the source-state diagnostic under `F-DIRTY-LAYER`, `reload` leaving the requested settings and the next synchronize showing it, attaching under a key, the handle's live stage under `F-CACHED-STAGE` (ICON-34), and a removed binding's handles raising. The API rows' save, reopen, and undo parts wait for `F-BINDING-STATE`. Not applying the requested payload policy, or not recording the time code, fails a test.

#### Phase D log

- **D1, copy-route probe.** `tools/feasibility/probe_copies.py` tags a binding's scene, destination collection, and managed object with ID-property records. The scene and the collection point at each other, and the object points at the collection. A file-level index names the destination too. The probe runs the copy routes the spec names that background mode can drive, and checks the outcomes D2 builds on ([Copy routes](../feasibility/runtime-record.md#copy-routes-m3)).
  - Linking a collection and duplicating a managed object are recorded too: linking brings another candidate with the same identity, and object duplication copies ownership tags.
  - Every route that ran copies the identity, and the records survive save and reopen.
  - The full-copy scene, append, and link copy both sides of the pair, and rewrite the copies' pointers to each other. So on those routes, the mutual-reference rule finds two pairs and can't decide. On the other routes, one pair remains.
  - Duplicating the destination collection is covered only by `Collection.copy()`, a shallow copy whose shared objects keep tags naming the original collection.
    - Outliner > Duplicate Collection, the deep copy, can't run in background mode.
    - Its outcome is inferred from the full-copy route, not tested: the collection copy forms no new pair, and the object copies name it, so the tags and the records disagree.
    - `F-OWNERSHIP-AMBIGUITY` builds that state for COPY-01 (D10).
  - An ID pointer in a record makes its target a dependency of append and link, and holds a user. An unlinked destination stays in the file while a record points at it. Removing it clears every pointer to `None`. D4 weighs both when placing the records, and D9 handles a destination that is gone.

    - Appending a host itself gives a second index, until the save drops the appended host, which has no users.

- **D2, the canonical-candidate rule** (with the user). [Canonical Candidate](../spec/source-access.md#canonical-candidate) adds a binding index to each `.blend`. It names each binding's destination and is held outside the bindings' own datablocks, which D1 found no copy route reaches. The index is persisted binding state ([Binding State](../spec/lifecycle.md#binding-state)).
  - The rule:
    - The candidate the index names is canonical, when its record and destination refer to each other.
    - Without a usable entry, the one mutually referring candidate is canonical.
    - Otherwise every candidate is disabled.
  - So on the full-copy scene and append, the original stays enabled. A lost index degrades to mutual reference, not to disabling everything. Two indexes, or an index that disagrees with the records, disable every candidate rather than guessing.
  - Linked bindings are not candidates: they are read-only library data whose identity belongs to their library.
  - New rows: COPY-06, the index; COPY-07, its entry on creation; COPY-08, removal, delivered by M11; COPY-09 to COPY-11, the rule's three cases; COPY-12, linked bindings.
  - Left to later commits:
    - D4 places the index, and the records, so that a record and its destination refer to each other.
    - D10 decides whether detection restores a missing entry once the fallback has decided.
- **SCHEMA-04 split, before D3** (with the user). SCHEMA-04 keeps preserving unreadable or unsupported pending-cleanup records, and refusing to overwrite them, which M3's record framework delivers. Its disposal half moves to SCHEMA-06, delivered by M5: never authorizing disposal, and refusing the operations that interpret those records. Nothing disposes of resources before M5. M5's Tests section names `F-SCHEMA-VERSIONS` for it.
- **D3, the versioned record framework** (with the user, in one Blender-side module). Records exist only as ID properties and only Blender-side code reads or writes them, so the framework lives in `proscenium/records.py`, not in the bpy-free core.
  - **Schemas:** a `Schema` names the frozen dataclass a current-version record loads as, and one migration, on plain values, from each version below it to the next. Every version from 1 migrates.
  - **Typed records:** the code that uses a record reads typed fields that ty checks. Constructing the dataclass rejects missing and unknown fields. A record class checks a field's value in `__post_init__` where a hand-edited value would mislead, and that check's failure is a refusal too.
  - **Loading:** `load` returns `Loaded` at the current version, or a `Refused` value saying why: newer, migration failed, invalid, or unreadable.
    - Migrations run on a copy.
    - Any exception, in a migration or in constructing the record, is a refusal, since stored data must never crash the extension.
  - **Storage:** an ID's records are in one group, `id["proscenium"]`, one record per key.
    - Reading never writes. A migrated record is stored at the current version only when the extension next writes it, so opening a file changes nothing, and a downgraded extension can still read it until then.
    - `write` raises `RecordRefused`, changing nothing, over a stored record that `load` refuses, so the extension never destroys a record it can't read.
    - Blender converts a whole record before storing it, so a value ID properties can't hold, such as an int over 32 bits or a name over 63 characters, raises and leaves the stored record unchanged. The int case is tested; the name case was an ad hoc check.
  - **`F-SCHEMA-VERSIONS`** gets its generator: a three-version test schema stands in for the real schemas until they have older versions.
    - Its cases join once every row it lists has a test. SCHEMA-03 needs synchronization to refuse a binding whose records are refused, which comes with D4, along with the "unsupported record" diagnostic.
  - **Tests,** in `blender/`:
    - each fixture record through `load`, each refusal's message, migrations on copies, and the schema's own checks;
    - records with ID pointers through save and reopen;
    - reading leaving the stored records and the file's dirty state unchanged;
    - writing refused over every unreadable record;
    - a failed Blender write leaving the record intact.

- **The time code is the attempt's, not a setting, before D4** (with the user). A synchronization's time code is derived at synchronization time, so the binding's configuration doesn't store it. Its requested settings are the payload policy, conversion, and purpose.
  - The last attempt records the time code it used, as the published generation already does.
  - API-02 now checks that synchronizing changes no setting and uses the requested ones.

  - `RequestedSettings` loses its time code, and synchronizing no longer records one.

- **D4, binding configuration** (as sketched with the user). A binding's records are in Blender data, read at every call. Its source stages and attachment stay runtime state, made from the records on first use.
  - **Records** (`proscenium/bindings.py`), each at version 1:
    - The configuration is on the target scene, under `binding.<identifier>`. The identifier is a UUID4 hex string.
    - The configuration holds the source (a file path as given, so a `//` path is relative to the `.blend`; or a source key, with the root-layer identifier of the stage last attached), the destination, and the payload policy.
    - The source kind and the payload policy are `StrEnum`s: `SourceKind`, in the core beside the source classes, and `PayloadPolicy`, which gives its `Usd.Stage.InitialLoadSet`. ID properties store them as their plain string values (one check), and the configuration converts them back when it loads; an unknown value is a refusal.
    - The destination collection carries a tag that names the binding and points back at its scene, so a record and its destination refer to each other as the canonical-candidate rule requires.
    - The binding index is a record on a Text named `.proscenium`, with a fake user, found by its record. Blender 5.2.2's datablock search menus leave out dot-prefixed names while the `show_hidden_ids` preference is off, its factory default (`id_search_allows_id`; checked in Blender's source and the preference's default, not in a drawn UI).

    - Conversion and purpose settings are M6's: they join the configuration as version 2, and BIND-06 moves to M6, whose Tests section and the registry name `F-MULTI-BINDING`.
  - **Synchronization API:** it moves to `proscenium/synchronization.py`, since creating, finding, and attaching bindings are Blender operations. Its tests move to `blender/`.
    - Handles look a binding up in the scenes' records at every call. A handle whose record is gone, after undo of creation for example, raises `BindingNotFound`. D8 replaces the scan with an index.
    - `set_settings` writes the payload policy and returns a `Result`.
    - A binding whose configuration can't be read keeps it, and its synchronize, `set_settings`, and `reload` return a fatal-failure result with an `UNSUPPORTED_RECORD` diagnostic carrying the refusal's message.
  - **The key contract reads the records.** The root-layer identifier is binding configuration, which undo restores, so a runtime copy would drift from it. `attach` finds the bindings with the key in the records, checks confirmation against their stored identifiers, attaches their runtime sources, and stores the new identifier.

  - **Registration:** the extension registers an empty `proscenium` property group on Scene, Collection, and Text, and a persistent `load_post` handler that drops runtime sources. So after reopening, a file binding has no live stage and an attached binding's source is unavailable until the caller attaches.
  - **Relative paths:** creating a binding refuses a `//` path in a file that was never saved, since nothing anchors it. The runtime source resolves its path at each use, so after Save As to another folder, the next synchronization opens the file beside the new `.blend`.
