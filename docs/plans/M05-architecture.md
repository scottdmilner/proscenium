# M5 — Synchronization architecture, diagnostics, and failure safety: plan

How M5 will build the synchronization transaction, its diagnostics and binding state, persistent cleanup tracking, and `cache`'s API and failure safety, against a stub application layer, and the order of work. Requirements are in the [M5 milestone](../milestones/M05-architecture.md); where this plan and a requirement file disagree, the requirement file wins. Mechanisms named here are suggestions unless marked settled. Each phase gains a short decision log once work starts, in the style of the [M4 plan](M04-prototypes.md).

M5 delivers the matrix rows whose `delivery` is M5: BND-01 to BND-03, TXN-02 to TXN-10, CACHE-02, CACHE-03, CACHE-05 to CACHE-07, DIAG-01 to DIAG-11, BIND-05, API-04, API-05, API-09, CONS-01, CONS-03, LAYER-02, UNDO-01 to UNDO-05, UNDO-09, STATE-02 to STATE-04, STATE-08, PEND-01 to PEND-06, DEST-05 to DEST-09, REOPEN-01, SCHEMA-06, XFORM-12, TLAY-03, and AFAIL-01 to AFAIL-03. It settles the DECISIONS.md rows it owns or co-owns: "Pending-cleanup persistence contract" (the mechanism), "Pending-cleanup tracking mechanism", "Post-publication retirement failure", "Pre-publication disposal failure", "Undo for failed synchronizations", "Undo step for a published synchronization", "Undo memory cost", "Removed destination", and the result's fields in "Synchronization API".

## Starting point

- **Every binding has an attached source** (DECISIONS.md "One kind of binding", 2026-11-03). `Bindings.create_binding(scene, ...)` makes an unattached binding, and the caller opens a stage and attaches it through `handle.attach(stage)`, which returns a `Result`; `handle.release()` releases it. Each binding's `BindingStages` (`binding/source_access/`, bpy-free) holds the attached stage and the binding's own evaluation stage, reused while the attached stage's root and session layers stay the same and dropped when either is replaced ("Evaluation-stage reuse"). After reopening a `.blend`, every binding is unattached, and so unavailable, until the caller attaches a stage again.
- **The API acquires sources and nothing more.** `api/bindings.py`'s `synchronize` acquires the evaluation stage through `BindingStages.acquire` and reports dirty layers; nothing is evaluated, planned, applied, or published. Its contract is settled (DECISIONS.md "Synchronization API" and "Time-sampled data representation", M4): `synchronize(time_code=None)` takes a numeric time code or `Usd.TimeCode.Default()`, and without one uses the target scene's current frame's, its subframe included. The code still requires a time code; the default is M5's to implement (XFORM-12, BIND-05).
- **The records exist and nothing writes them yet:** `Generation` (with `cached_time_codes`, M4 F3) and `LastAttempt` in `binding/persistence/binding_state.py`, at version 1, so M5 can still refine their fields. Manifests are written whole (`ownership_index.set_manifest`) or by entry (`ownership_index.set_manifest_entries`) through the bindings' state, and `ManifestEntry.role` is a free string. `binding/persistence/manifests.py` isn't among its package's exports yet; they gain it when M5 calls ownership, as that package's README says.
- **Results and diagnostics are a first cut:** `binding/results.py` (bpy-free) has three result states, six diagnostic categories (`source confirmation required` among them, for an attachment whose root-layer identifier changed), `Result.is_success`, and a `Diagnostic` without binding, source path, property or asset identifier, or fallback.
- **The compiled core has only the stage handle and error translation.** `proscenium/core/` is now the compiled core alone, and receives stages from `binding/source_access/`, never opening one. M1b's and M4's bridge (`tools/feasibility/hydra_bridge/`) holds the evaluation, planning, and application that M6 and M7 turn into product code. M5 takes two things from it: the plan's read-only buffers (`python_views.cpp`) as the model for the plan boundary, and `update.py`'s discipline (prepare in a collection no scene links, publish in one step that undoes itself on failure, retire what nothing outside the display uses) as the model for the transaction.
- **M4's decisions fix what is replaced:** partitions are a drawn copy, a batch, or one shared datablock (DECISIONS.md "Partition unit"), and a copy's identity comes from its source entity and its place among the copy's objects, as M4's tracks are keyed (M4 plan, E1).

## Settled with the user (2026-11-03)

1. **Plans come from a minimal path through the core.** The core builds the Hydra chain M6 will extend, captures each drawn gprim's source path, world transform, and bounds at a time code, and plans a placeholder for each into the real plan envelope. So `synchronize` and `cache` run end to end against the stub application layer, and source-change detection, time-varying bounds, and the default time code are tested on real evaluation. M6 replaces the capture and the planner; the envelope and the boundary stay. Rejected: plans built by hand in tests, which would need a plan builder in `src/` only tests use, and would leave CONS-03, CACHE-05, and BIND-05 without an evaluation to test.
2. **Pending cleanup is a separate ledger on the binding index's Text.** One versioned record, one entry per pending resource, holding what M3's contract lists: the owning binding, the resource's entry key in that binding's manifest, a pointer to its datablock, its originating operation, and its cleanup diagnostic, written only for a resource whose removal failed (Phase S). Chosen for the least overhead: the Text already exists wherever a binding does, `index_texts()` (`binding/persistence/configs.py`) already finds it, M3's copy-route evidence already shows no copy route reaches it (contract (6)), and removing a binding doesn't remove it, as M11 needs; with nothing pending, nothing on a hot path reads it. Rejected: pending state in the manifests, which adds a field every ownership-index rebuild reads and fails contract (6) while manifests are on destination collections; a Text of its own, which repeats M3's evidence and duplicate handling for no gain.
3. **A failed `cache` call records no last attempt.** The last attempt stays the most recent synchronization attempt, with the settings and time code it tried, so "displayed at 10, last attempt at 20 failed" keeps its meaning. A `cache` call returns its result; pending cleanup it leaves goes into the ledger with its diagnostic, as any operation's does.
4. **Removing a binding's destination collection or target scene removes the binding** (with the user, 2026-11-06; Phase S). Its records are on the destination, so a binding's candidates are collections alone.

## Phases

Each phase ends with a review by the user before the next starts. Each phase lists its commits in order. Every commit is one feature and passes `pre-commit` and the test suite on its own:

- A spec change lands with its matrix rows, its `invariants.md` bullet, and its DECISIONS.md row.
- A new fixture lands with its registry entry, its Named Contract Fixtures row, its mention in the milestone's Tests section, and a row that uses it.
- Code lands with its tests.
- A decision lands with its line in the phase's decision log.

If a commit grows past one feature, it splits, and this list is updated in the same commit.

### Phase B — The plan boundary in the core

1. **The Hydra chain, a minimal capture, the planning context, and the display-plan envelope,** in one commit, since the snapshot is opaque to Python and is tested through the plan (with the user):
   - **The chain and capture:** the core receives the evaluation stage `BindingStages.acquire` returns, as a weak stage pointer, and captures its terminal scene index at a time code into an immutable snapshot of each drawn gprim's source path (mapped back to the composed stage, never Hydra's path), world transform, and bounds, with nothing borrowed past the snapshot's life (SNAP-08, SNAP-10).
   - **The planning context:** an immutable value object with what the minimal planner reads (suggested: the target scene's unit scale and the representation version), captured in Python from the target scene before planning.
   - **The envelope:** partitions, ownership entries with their resource identities, roles, covers, and uses, correspondence entries, and placeholder content, each placeholder's bounds as a read-only `'f'` buffer. Deterministic over snapshot, settings, and context (PLAN-08, PLAN-09 are M6's; M5 keeps its planner deterministic so its tests can rely on it).
2. **Errors at the boundary:** Tf errors and C++ exceptions become Python exceptions at each entry point, none lost. The transaction turns them into fatal diagnostics before any Blender mutation in Phase D (item 13).
3. **Source-change detection:** evaluation is discarded when a contributing layer changes during it (CONS-03, `F-SOURCE-CHANGE`), and the binding's `BindingStages` keep a source revision the generation's synchronization is compared with (CACHE-05). Suggested: a `UsdNotice::ObjectsChanged` listener on the evaluation stage, counting changes; a generation from another session (every binding is unattached after reopening), or from before a reload, an attachment, or a dropped evaluation stage, counts as changed.

#### Phase B log

- **B1, the chain, capture, context, and envelope** (one commit, with the user: the snapshot has no Python reads, so it is tested through the plan). `core/scene_index_chain.h` holds `SceneIndexChain`: UsdImaging's scene indices without the draw-mode one, then the extComputation-primvar-pruning, implicit-surface, NURBS-approximating, and dependency-forwarding filtering scene indices, as the bridge chains them. It takes the stage as a weak pointer through a `StageHandle`, and `release()` drops the chain and the handle, so a dropped stage expires (`tests/isolated/test_stage_handle.py`). `capture(time_code)` runs without the GIL and copies each drawn gprim (a Hydra gprim type outside native and point instancing, whose sources and instance contexts are M6's) into a `Snapshot` of plain values: source path (the prim-origin path, else the Hydra path, which outside instancing is the USD path), world matrix, and local extent. `core/plan.h` holds `PlanningContext` (unit scale, representation version) and the envelope; the minimal planner gives each gprim a drawn copy's partition of an `object` that uses its `bounds mesh`, both covering the source, a correspondence entry for the object, and a placeholder with its world matrix and bounds as a 6-float `Vt.FloatArray`. It reads the representation version only, refusing any but 1, since coordinate conversion, which reads the unit scale, is off by default and M6's; the planning settings are M6's too, so `plan(snapshot, context)` takes no settings yet. Capturing the context from the target scene lands with the transaction (D1). A resource's identity is a value, its role, source entity, and place among the copy's objects, compared by equality as the bridge's plan diff compares entries; with the user, nothing digests it, and the manifest keys entries by random entry keys instead (DECISIONS.md "Ownership metadata format"), so content-keyed resources are rebuilt once after reopening ("Representation roles and resource identities"). `bpy_free/test_core_plan.py` checks the plan against the transaction scenes.
- **B2, errors at the boundary.** Every entry point that can post a Tf error runs through `Guarded` (`core/errors.h`), which raises its Tf errors as `Tf.ErrorException` and lets a C++ exception thrown with none posted take pxr_boost::python's translation. An exception thrown after Tf errors joins them as one more error, since the last error mark would otherwise report them through the diagnostic delegate, which prints them where Python can't read them. `_post_tf_error(message, then_throw=True)` checks that case, which nothing in USD reachable from the core triggers on demand; the other entry points' refusals are checked in `bpy_free/test_core_plan.py`. Turning these exceptions into fatal diagnostics needs the transaction, so BND-02 and BND-03 move to Phase D's failure injection (item 13).
- **B3, source-change detection.** `BindingStages.source_revision` is a `SourceRevision`, a process-unique string (a per-process UUID and a counter), advanced by a listener on the evaluation stage's `UsdNotice::ObjectsChanged` and by every attachment and dropped evaluation stage. So an edit to a composed layer, a reload that rereads one, and a caller's muting, interpolation, or mask, or a payload policy, that an acquisition matches each change it, and a no-op acquisition, a reload that rereads nothing, and edits to layers the stage doesn't compose don't (checked in `bpy_free/test_source_revision.py`). The listener holds only the revision, so it keeps no binding alive. The generation record stores the revision it was synchronized from (`Generation.source_revision`), so undo restores it with the generation, and one from another session never matches. `changed_layers()` gathers, while open, the identifiers of the evaluation stage's layers that `SdfNotice::LayersDidChange` reports changed, the caller's session layer included, for CONS-03's diagnostic. The transaction compares and discards (D), and `cache` refuses (E).

### Phase C — Diagnostics and results

1. **The diagnostic categories** of [Diagnostics](../spec/pipeline.md#diagnostics), pending cleanup and fatal failure included (DIAG-01), and the fields of A3 (DIAG-02).
2. **Aggregation and the result state:** repeated problems aggregate (DIAG-03); the state is derived from the categories (DIAG-09 to DIAG-11), source state informational.
3. **Where diagnostics live:** the generation's and the last attempt's own, the result's attempted time codes, and an unchanged refresh's equivalent diagnostics (DIAG-07). The ledger's cleanup diagnostics and the result's cleanup status need the ledger, so they are Phase D's (items 4 and 5).

#### Phase C log

- **C1, the categories and the fields** (with the user: a code determines its category and severity). `DiagnosticCategory` holds the nine categories of [Diagnostics](../spec/pipeline.md#diagnostics) (DIAG-01). `DiagnosticCode` is the documented list of stable codes (DIAG-14), each with one category and one severity in a table beside it, so a diagnostic stores its code and reads the other two from it, and none can hold a code under the wrong category; codes are added as each phase reports them. The four categories binding operations reported before outside the spec's nine are fatal-failure codes: `source-confirmation-required`, `unsupported-record`, `removed-destination`, and `copied-binding`; an unattached binding's is `no-attached-stage`, and a dirty layer's `unsaved-layers`. `Diagnostic` names its binding and holds DIAG-02's fields, each empty where it doesn't apply: source path, property path, asset, fallback, layers, and a pending-cleanup diagnostic's resource and role (its resource is its ledger key, D4). `Severity` gains `warning` for the content categories. Tests identify diagnostics by code.
- **C2, aggregation and the result state.** A `Result` holds only its diagnostics: its state is derived from them (`result_state`), each category giving success (source state), completed with issues (the content categories and pending cleanup), or fatal failure (an unavailable source and fatal failure), and a result taking its worst diagnostic's (DIAG-09 to DIAG-11). The last attempt derives its result the same way, so no record holds a state its diagnostics contradict. A result aggregates its diagnostics on construction (`aggregated`, DIAG-03): a problem is a diagnostic's code and everything it concerns, apart from its message, so a repeat is dropped, the first report kept, in the order first reported. Pending cleanup and the content categories have no codes until a phase reports them, so their states are checked in the table the derivation reads (`bpy_free/test_results.py`); F-RETIREMENT-FAILURE and F-PREPARATION-CLEANUP-FAILURE check them through synchronizations in Phase D.
- **C3, where diagnostics live.** The generation and the last attempt already hold their own diagnostics in separate records (M3; `blender/test_binding_state.py` checks that writing one leaves the other). A `Result` gains `time_codes`, the time codes its operation attempted (A3, API-13): a synchronization's one, whether it publishes or fails, and none for the other operations so far; `cache`'s are Phase E's. Two synchronizations of F-DIRTY-LAYER with nothing changed between them report equal diagnostics in the same order (DIAG-07). With the user, the cleanup status and the ledger's cleanup diagnostics move to Phase D (items 4 and 5), which build the ledger and report it.

### Phase D — The transaction against the stub application layer

1. **Where it lives:** suggested, a package beside `binding/` and `core/` holding the transaction and the stub application layer, which M7 replaces. `api/` imports it, and it imports `binding`'s units and `core` through what each exports, as `api/` does. Its row joins the import-rules table in `src/proscenium/README.md`, AGENTS.md's Layout, and `tests/bpy_free/test_import_tiers.py`. The ledger's record goes in `binding/persistence/` and its write-through in `binding/runtime/`, each exported from its package.
2. **The role `StrEnum`** in the manifest entry, stored as the same string; an unknown role is a refusal. **Entry keys and places:** entries are keyed by random entry keys, `uses` names entry keys, and a copy's roles record their place; a prepared resource takes the key of the published entry whose identity it has, else a new one. The manifest stays at version 1, since no release has written one. `binding/persistence` exports the manifests from here on.
3. **The stub application layer:** one placeholder object and bounds mesh per partition, prepared in a staging collection no scene links (TXN-05).
4. **The ledger, and preparation tracked in it before fallible work:** the ledger's record and its write-through; each prepared resource enters the ledger as prepared work before the next fallible step (TXN-08); reused published resources are never disposal candidates (TXN-09); disposal resolves each entry it removes, and leaves each it can't retryable, with its cleanup diagnostic.
5. **The cleanup status** (from C3): each result gains a cleanup status, the ledger's current cleanup diagnostics aggregated by operation and resource, apart from its own diagnostics and never changing its state (A3, DIAG-06, DIAG-15).
6. **Publication:** the manifest written whole, the generation record, and the destination's contents switched together, undoing itself on failure (TXN-06); the last attempt recorded on every outcome (STATE-02, STATE-03); and F-FAILED-SETTINGS checks the generation's and the last attempt's diagnostics apart (DIAG-04).
7. **Retirement:** the old generation's obsolete resources removed through the bindings' state, or published out of the manifest before removal, so a removal costs what it removes; leftovers stay in the ledger, noncanonical and excluded (TXN-07).
8. **Failed disposal before publication:** the attempt stays fatal, reports both failures, and leaves only inactive tracked leftovers (TXN-03, TXN-04, TXN-10), whose cleanup diagnostics a later attempt never erases (DIAG-05).
9. **Cleanup retry:** an explicit operation (suggested, `handle.retry_cleanup()` delegating to `Bindings`, as the handle's other methods do; M11's cleanup builds on it) that rereads the ledger, revalidates ownership and current users, disposes or releases intact, and removes resolved entries and their diagnostics, without USD access (PEND-01 to PEND-04, DIAG-08); an unreadable or unsupported ledger refuses and disposes of nothing (SCHEMA-06).
10. **The time code, as settled:** `synchronize(time_code=None)` evaluates at the time code given, numeric or `Usd.TimeCode.Default()`, and without one at the target scene's current frame's, its subframe included; the last attempt and the generation record the one used (XFORM-12, BIND-05, `F-MULTI-BINDING`).
11. **Non-reentrancy:** while a synchronization, `cache` call, or cleanup retry runs, `synchronize`, `cache`, `attach`, `release`, `reload`, and `retry_cleanup` on any binding raise; `set_settings` doesn't (CONS-01, CONS-04, API-05). Suggested: a flag on `Bindings`, set at entry and cleared in a `finally`.
12. **Undo:** pushed by `Bindings` in `api/`, the layer above synchronization that every Python API call passes through, never by the `synchronization` package (with the user, 2026-11-05): one step per publication, and per cleanup retry that commits, through `ed.undo_push`, none for a failure, none in background mode or with global undo off, and none doubled when an operator calls the API (UNDO-02 to UNDO-04); undo marks the binding possibly out of date (UNDO-05); undo restores the ledger with ownership (PEND-05). Undo after deleting stub content leaves the bindings' runtime state (`binding/runtime/`) and its ownership index consistent; a binding's attachment survives the undo, and a binding whose creation was undone keeps it for redo (UNDO-06).
13. **Failure injection:** a test at each boundary (acquisition, evaluation, planning, each preparation step, publication, retirement, disposal), where a failure at acquisition, evaluation, or planning, the core's errors included, is a fatal diagnostic before any Blender mutation (BND-02, BND-03), patching the step's module function as the runtime tests already do, with no hooks in `src/`. The before-publication checks compare the whole published generation, not only its objects (TLAY-03); the same tests rerun unchanged against M7's application layer.

#### Phase D log

- **D1, where the transaction lives** (with the user: the package is `synchronization`, and the ledger's record and write-through land with D4, which first records prepared work). `proscenium/synchronization/` holds the transaction (`transaction.py`), and will hold the stub application layer. `Bindings.synchronize` finds the binding, refuses one that isn't usable, and calls `synchronization.synchronize(binding_id, config, current_stages, time_code)`, which holds the steps that exist so far: the removed-destination refusal, acquisition, and the source-state diagnostic. It fetches the binding's stages only once it accesses the source, so a binding refused before that gets none, as before. The package's row is in `src/proscenium/README.md`'s import rules, AGENTS.md's Layout, and `tests/bpy_free/test_import_tiers.py`: it may import `binding`'s units and `core`, and `api` may import it.
- **D2, roles, entry keys, and places.** `RepresentationRole` is the decision row's vocabulary, stored as its string; an entry naming another role is refused as invalid, and `synchronize` refuses a binding whose manifest can't be read with `unsupported-record`, before reading its source (ROLE-01, on F-SCHEMA-VERSIONS' "unknown-role"). Entries are keyed by `new_entry_key()`'s 32 hex digits, which a manifest checks, and `uses` names entry keys. A copy's roles (`object`, `shear parent`, `bounds mesh`, `action`) cover one source entity and record their place; other roles record none. An entry's `identity` is its `CopyResourceIdentity` (role, entity, place), or None for a content-keyed role, and `entry_keys(manifest, identities)` gives each prepared resource the key of the published entry with its identity, else a new one (ROLE-05). The manifest stays at version 1. `binding/persistence` exports the manifests, so the ownership index's import exception is gone. Tests name entries through `tests/support/manifests.py`'s `key(name)`.
- **D3, the stub application layer.** `synchronization/application.py`: `new_prepared_work()` makes a `PreparedWork` with its staging collection, which no scene links; `prepare(plan, published, prepared)` makes each placeholder's bounds mesh (the eight corners of its bounds, or none) and an object drawing its bounding box at the plan's world transform, adding each datablock to `prepared` as it's made, so a failure partway leaves everything made to dispose of; `dispose(prepared)` removes it all. The entries it makes are the manifest a publication writes, each taking the key of the published entry with its identity (D2). It only creates datablocks, so nothing the published generation reaches changes (TXN-05); the oracle's failure injection on F-PREPARATION-CLEANUP-FAILURE lands with D4 and D13. The transaction calls it from D6, once prepared work is tracked (D4) and published; until then nothing would track or publish what it made. A sheared world transform, which needs a shear parent, is M7's.
- **D4, the ledger, and preparation tracked in it** (with the user: D4's cleanup status became D5, and a cleanup diagnostic's resource names its ledger key). `binding/persistence/ledgers.py` holds the `Ledger` record on the binding index's Text, keyed by random ledger keys, each `LedgerEntry` holding the contract's evidence: the binding, its entry key and role, a pointer to its datablock, its `OriginatingOperation`, its `RetryStatus` (`prepared` while its preparation runs, `retryable` once its disposal fails), and its cleanup diagnostic, which a retryable entry has and a prepared one lacks. - **D5, the cleanup status.** A `Result` gains `cleanup_status`, the binding's current cleanup diagnostics, aggregated apart from its own; it holds only pending-cleanup diagnostics, and the state derives from the result's own diagnostics alone, so leftovers an earlier attempt left never change it (DIAG-06, DIAG-15). `pending_cleanup.cleanup_status(binding_id)` reads it from the ledger: each retryable entry's diagnostic, by ledger key, and none for prepared work, which its operation still tracks. - **D11, non-reentrancy** (with the user: a cleanup retry is exclusive too, and `retry_cleanup` raises with the others, since a retry removes datablocks and writes the ledger, and one during a synchronization would remove that attempt's prepared work; CONS-04, Source Consistency, invariants.md, and the "Synchronization API" row say so). `Bindings.running` is the flag: `synchronize` and `retry_cleanup` are `_exclusive`, setting it at entry and clearing it in a `finally`, and they, `attach`, `release`, and `reload` are `_not_while_exclusive`, raising `ReentrantCallError` before anything runs, the refresh of the bindings' state included; `set_settings`, the queries, and `create_binding` are unguarded. - **D12, undo** (with the user: background mode pushes no step, as the spec says, so tests patch the guard; an operator calling the API declares no `UNDO`; undo marks a binding possibly out of date when its generation changed). `Bindings.synchronize` pushes one step with `ed.undo_push` once the transaction has published, and `Bindings.retry_cleanup` once the retry has committed, so neither the `synchronization` package nor a failure pushes one. A mutation check (pushing twice, or never) failed the five step-count tests.

### Phase S — Simplification (with the user, 2026-11-06)

A review against the feasibility bridge found most of Phase D's size in two places: persistent tracking of failures nothing realistic triggers, and binding records kept apart from the destination so a binding could outlive it. These commits replace those mechanisms of D4, D7, D8, and D9; code built for later milestones (incremental manifest writes, ownership queries, the persistent selection) stays.

1. **The contracts:** the spec, `invariants.md`, matrix rows, and DECISIONS.md rows below, with the milestone files. Pending cleanup is written only for a removal that fails (TXN-08, STATE-04, PEND-01); a failed write to the pending-cleanup ledger is a defect and raises (API-05); removing a binding's destination or target scene removes the binding (STATE-08, DEST-05 to DEST-10, which replace DEST-01 to DEST-04); and the canonical candidate is the one the index names, without the mutual-reference fallback (COPY-09, COPY-11, COPY-13, COPY-14, COPY-19; COPY-10 retired). 2. **Tracking by the attempt:** prepared work and the obsolete resources are held by the attempt, and the ledger gets an entry only for a resource whose disposal or retirement failed. The ledger's statuses and `retry_status` go; its version 1 changes in place, since no release has written it.
3. **One removal:** disposal, retirement, and a cleanup retry mark what they remove and share one routine, users first, a level at a time, releasing intact what anything else uses (suggested: `cleanup_retry`'s, by `bpy.data.user_map`).
4. **Defects raise:** the transaction's and the cleanup retry's handling of a ledger write that fails goes, with the messages only it used.
5. **Binding records on the destination:** the configuration, with a pointer to its target scene, and the last attempt join the generation and manifest on the destination collection; the scene's records and the destination tag go. Candidates are local collections with a record whose target scene exists, the rule reads only the index, and a binding whose destination or target scene is removed no longer exists. Fixtures and tests of the COPY and DEST rows follow.
6. **The contracts for no runtime cache** (with the user, measured: [runtime record](../feasibility/runtime-record.md#lookups-without-the-bindings-cache-m5-phase-s)): COPY-18 (detection at every lookup), and UNDO-07's and REOPEN-01's oracles; DECISIONS.md "Binding records read when called", "Manifest writes: whole and per entry", and "Copied-binding detection"; and the milestone files.

Lookups read the records when called, ownership comes from a datablock's users, the ledger is read from the index's Text, and a synchronization reads its manifest once and passes it to publication. The ownership module is named for what it holds.
8. **Updates that can't name a datablock twice** (with the user): a per-entry update gives each changed entry without its datablock, which is the one the operation made for its key or the one its entry already names.

A generation at the default time code caches nothing and succeeds before reading the source (CACHE-06). Synchronizing again already gave a generation of its own time code alone, retiring the actions with their objects (CACHE-07). `blender/test_caching.py` checks, on F-SOURCE-CHANGE "changed-before-cache", that after an edit, a reload of the rewritten file, or attaching again, cache fails with that diagnostic and changes no generation, manifest, or action, for new and cached time codes alike, and caches once synchronized again, while without a change it keeps caching; that a binding with nothing published refuses; on "default-time-code", that a call succeeds with no time codes attempted and nothing changed; and on "synchronize-again", that the generation at 10 has no cached time codes and no action, and shows 10's translation at every frame. A mutation check (no revision comparison) failed the edit, reload, and attach cases, each run alone.
