# Decision Register

Milestones update this register when they settle a decision. Every in-scope requirement is traced in the requirement-to-test matrix created in M1, with high-risk entries marked separately by M4. Settled contract decisions update their requirement rows and test/oracle coverage before implementation. Fixture IDs refer to [Named Contract Fixtures](testing/strategy.md#named-contract-fixtures).

| Synchronization API | M3 | **Chosen (with the user, 2026-10-16):** callers reach a binding through an immutable handle that holds only its persistent identifier, never a datablock or cached state, so undo, redo, and file loads can't leave it stale (UNDO-07); a handle whose binding is gone raises for methods that need records; release remains valid. `handle.synchronize(time_code=None)` synchronizes at the time code it is given, or without one at the target scene's current frame's, and `handle.cache(time_codes)` caches other time codes in the published generation (row "Time-sampled data representation", 2026-11-02). The time code is the attempt's, not a stored setting (with the user, 2026-10-19): callers derive it at each synchronization, so a binding's configuration holds only the requested settings, which change only through `handle.set_settings(...)` and don't synchronize. The last attempt and the published generation record the time code they used. Synchronizing returns an immutable result with the result state and diagnostics; expected failures are results, and exceptions report only misuse. Creating bindings, finding a scene's bindings, and reporting copied bindings belong to the process's bindings. Attaching and releasing belong to each handle. Methods delegate to functions keyed by identifier, which tests exercise. `handle.reload(layers=None)` rereads source layers on request without synchronizing (row "Dirty layers and reloading", 2026-10-18). `handle.retry_cleanup()` retries the cleanup earlier attempts left pending, explicitly and without USD access; M11's cleanup builds on it (M5 D9). M3 settled the module and names: `proscenium.api.bindings`, whose `BINDINGS` is the process's `Bindings`. **The result's fields (M5, with the user, 2026-11-03):** the result state; the operation's own deduplicated diagnostics, with a pending-cleanup diagnostic for each resource it left pending; the time codes it attempted; and the binding's current cleanup status, apart from its own diagnostics (DIAG-06). The state derives from the operation's own diagnostics, so cleanup an earlier attempt left pending doesn't keep a later synchronization from succeeding. A diagnostic holds a stable code naming its problem (such as `untranslated-type`), which gives it one category and one severity (M5 C1, with the user, 2026-11-04), and its message, binding, source path, property path, asset, fallback, the layers it concerns, and for pending cleanup its resource's ledger key and role, so callers and tests identify it without reading its message. **Non-reentrancy (M5, with the user, 2026-11-03):** while a synchronization or `cache` call is running, `synchronize`, `cache`, `attach`, `release`, and `reload` on any binding raise before changing anything; `set_settings` is allowed, and the running attempt keeps the settings it started with. Process-wide, since every binding shares the file's ledger, the undo step a publication pushes, and the bindings' runtime state. The GIL doesn't prevent a nested call: one can come on the same thread from a Blender handler or a USD notice the transaction triggers, or from another thread while the core captures without the GIL. A flag that `Bindings` holds suffices, since only code holding the GIL reads or writes it. See [Synchronization API](spec/source-access.md#synchronization-api). | M3 and M5 API tests |
| Runtime indexes hold checked ID references | M3 | **Chosen (with the user, 2026-10-20):** the bindings' runtime state (`proscenium/binding/runtime/`) is a disposable write-through cache of their records: rebuilt after file load, undo, and redo, and when the file's scenes change, and never read back from the records after the extension's own writes. It holds references to datablocks, never to data inside one, and checks each before returning it, so no lookup returns a removed datablock: a removed datablock's check rereads the one manifest that names it, and a removed scene or destination rebuilds the cache, which then answers again. Bindings are keyed by binding identity, and claims by Blender's `session_uid`, which no other datablock in the session gets: a new datablock often takes a removed one's address. Chosen because no persistent identifier finds a datablock without a scan (names change on rename, and Blender has no lookup by `session_uid`), so a cache holding no references would scan `bpy.data` on every hit, which M7's selection mapping can't afford. Rejected: a generation counter that makes stale lookups fail, since the checks answer them from current data instead. Data inside a datablock is never held: a modifier held across undo read freed memory (one check, [M3 plan](plans/M03-bindings.md), D8). See [Undo and Runtime State](spec/lifecycle.md#undo-and-runtime-state). | `F-BINDING-STATE` |

Without a usable index entry, it is the one candidate whose record and destination refer to each other. Otherwise every candidate is disabled. | Ownership metadata format | M3 | **Chosen (with the user, 2026-10-19):** each binding has a **manifest**, a record on its destination collection with one entry per managed resource. An entry names the resource's datablock (an ID pointer), the source entities it covers (composed-stage paths), its representation role (M5's vocabulary), its place among its copy's objects for a copy's roles, and the managed resources it uses, by their entry keys. **Entry keys (M5 B1, with the user, 2026-11-04)** are random 128-bit identifiers, 32 hex digits, given when a resource is first published and kept while its entry lives, since an ID-property key holds at most 63 bytes and source paths exceed it; a key is never the resource's identity, which the entry's fields give (row "Representation roles and resource identities"). Ownership is which binding's manifest holds the entry. Managed dependents are derived by inverting the uses, and unmanaged users are read from Blender's user graph when an operation needs them, since nothing persistent can track them. Nothing is stored on the managed datablocks: a datablock is managed by the binding whose manifest names it, so a duplicate or appended copy of managed content is unmanaged with nothing to reconcile, and content two manifests name is ambiguous. Chosen because ownership tags on every datablock duplicated what the manifest records: on 10,000 objects each record kind added about 1.1 MB to the `.blend`, and reading the whole manifest through the record framework took 32 ms (one ad hoc run, macOS), so hot paths use runtime indexes built from it (M3 Phase D). | Manifest writes: whole and per entry | M3 | **Chosen (with the user, 2026-10-20):** a manifest is written whole (`ownership_index.set_manifest`), for a binding's first publication and Phase 1's full rebuilds, or by entry (`ownership_index.set_manifest_entries(binding_id, changed, removed)`), for Phase 2 refreshes that change some resources. Only its entries are written, staged so a value or key ID properties can't hold changes nothing; a record at an older version is written whole. The ownership index changes only those entries' claims, and an empty update writes nothing, as a no-op refresh must ([Affected Content](spec/incremental.md#affected-content)). Chosen because a whole write pays for every entry: publishing a one-resource change to a 10,000-entry manifest took 51–68 ms whole and 0.7–1.1 ms as an update, 0.02–0.05 ms at 100 entries (bpy wheel, 5 runs each); what's left is copying the entries in memory and, for removals, a scan of the uses. Not measured: the undo memory a step keeps for a changed manifest, which no Python API reports; an undo push took 10–22 ms on 10,000 objects whatever changed. Rejected: updates alone, where a full rebuild would name every old resource as removed. See the [M3 plan](plans/M03-bindings.md), D8. | `blender/test_indexes.py`, `blender/test_ownership.py`, `blender/test_records.py` |
