# Decision Register

Milestones update this register when they settle a decision. Every in-scope requirement is traced in the requirement-to-test matrix created in M1, with high-risk entries marked separately by M4. Settled contract decisions update their requirement rows and test/oracle coverage before implementation. Fixture IDs refer to [Named Contract Fixtures](testing/strategy.md#named-contract-fixtures).

| One kind of binding | M3 | **Chosen (with the user, 2026-10-18):** every binding has a source stage, the stage its source is composed on, which is also its live stage. Its source is a **file source**, whose source stage the binding opens itself outside every stage cache, or an **attached source**, whose source stage a caller attaches under a source key. One rule set covers both: the binding evaluates an evaluation stage, which composes the source stage's root and session layers, matching its mask, muting, and interpolation, under the binding's own payload policy, and never changes the source stage's settings; layers are displayed as loaded and reloaded only on request (row "Dirty layers and reloading"). What differs is only who opens the source stage, when the source is unavailable (an unattached or released stage, or a file that can't be opened), and what is saved (a path, or a key and root-layer identifier). When the binding opened the source stage itself, there are no caller's settings to protect, so the evaluation stage is the source stage: a second stage over ALab's loaded layers cost 259–289 ms and 36 MB in three ad hoc runs (macOS). Rejected: separate file-backed and in-memory bindings, whose contracts differed only where they treated loaded layers differently. See [Source Stages](spec/source-access.md#source-stages). | `F-CACHED-STAGE`, `F-PRIVATE-STAGE`, `F-REATTACH`, `F-MULTI-BINDING` |
| Dirty layers and reloading | M3 | **Chosen (with the user, 2026-10-18):** bindings display their source's layers as they are loaded in the process, unsaved in-process edits included, and synchronization never reloads a layer. A synchronization that displays dirty layers reports an informational source-state diagnostic naming them, which doesn't change its result state. Layers are reloaded only on request, through `handle.reload(layers=None)`: it rereads the binding's contributing layers whose files changed and every dirty one, which discards its edits, or only the named contributing layers. Saving edits first is the caller's responsibility. Chosen so a binding shows work in progress instead of refusing to, and so reloading, whose effects reach every stage sharing the layers, happens only when a caller asks for it. Rejected: failing synchronization on dirty contributing layers, which kept users from seeing edits in progress; evaluating the disk state through a private disk view (row "Private disk view feasibility"). | Strictness of the file-backed refresh contract | M3 | **Chosen (with the user, 2026-10-15): a binding with a file source keeps and reuses its own source stage** (row "One kind of binding"). The binding opens it outside every USD stage cache and never shares it with other bindings or tools. Refresh displays the layers as loaded; after a requested reload (row "Dirty layers and reloading"), the reused stage matches a stage newly opened from the same files. The source stage's anonymous layers (its session layer and those beneath it) compose into the display, so a future editor can show unsaved edits through the live stage without saving to disk; synchronization never authors them, and they are not saved in the `.blend`. This stage is the binding's live stage; callers get it from the binding, which never places it in a stage cache. Chosen because a new stage per refresh pays the open and the Hydra chain's construction again (0.58 s and 0.41 s on ALab, [record](feasibility/runtime-record.md#measurements-m1b-phase-e)) and resets the scene-index population, losing the notices Phase 2 can use (M13). **Change check (with the user, 2026-10-17):** a reload uses USD's non-forced reload, which goes by modification time, leaves unchanged clean layers alone, and always rereads dirty ones. A forced reload would notify every stage using each layer even when unchanged. Tested by comparing a reused stage with a newly opened one. | Releasing an attached stage | M3 | **Chosen (with the user, 2026-10-20):** a binding holds its attached stage until the caller releases it with `release(key)`, which releases it from every binding with the key, or attaches another stage under the key; loading a `.blend` releases it too. Dropping the caller's own references releases nothing, so the stage stays alive with its layers and their unsaved edits, which a stage opened on the same files sees; a released binding is unattached. A binding that no longer exists, as after undo of its creation, keeps its attachment, so redo brings it back attached (UNDO-06), and `release(key)` still releases it; its other runtime stages are dropped. Chosen because the evaluation stage composes the attached stage's root and session layers and so keeps them alive whatever holds the stage, and USD sends no notice when a stage is destroyed, so a binding can't let go of them when the caller does: a probe found an edit the caller had discarded still in a fresh `Usd.Stage.Open` until the binding's next acquisition, and a `weakref.finalize` on the caller's `Usd.Stage` never ran for a stage a `Usd.StageCache` held ([M3 plan](plans/M03-bindings.md), C9). Rejected: opening the evaluation stage at each synchronization, which would cost what a second stage over ALab's loaded layers did, 259–289 ms (M1); holding the stage weakly and letting go of the layers at the next acquisition, which left them loaded for an unbounded time. **Cost:** the caller's stage stays in memory beside the evaluation stage until it is released. | Synchronization API | M3 | **Chosen (with the user, 2026-10-16):** callers reach a binding through an immutable handle that holds only its persistent identifier, never a datablock or cached state, so undo, redo, and file loads can't leave it stale (UNDO-07); a handle whose binding is gone raises when used. `handle.synchronize(time_code)` synchronizes at the time code it is given. The time code is the attempt's, not a stored setting (with the user, 2026-10-19): callers derive it at each synchronization, so a binding's configuration holds only the requested settings, which change only through `handle.set_settings(...)` and don't synchronize. The last attempt and the published generation record the time code they used. Synchronizing returns an immutable result with the result state and diagnostics; expected failures are results, and exceptions report only misuse. Creating bindings, finding a scene's bindings, reporting copied bindings, and attaching or releasing under a source key span bindings, so they belong to the process's bindings, not to a handle. Methods delegate to functions keyed by identifier, which tests exercise. `handle.reload(layers=None)` rereads source layers on request without synchronizing (row "Dirty layers and reloading", 2026-10-18). M3 settled the module and names: `proscenium.api.bindings`, whose `BINDINGS` is the process's `Bindings`; M5 settles the result's fields. See [Synchronization API](spec/source-access.md#synchronization-api). | M3 and M5 API tests |
| Runtime indexes hold checked ID references | M3 | **Chosen (with the user, 2026-10-20):** the bindings' runtime state (`proscenium/runtime/`) is a disposable write-through cache of their records: rebuilt after file load, undo, and redo, and when the file's scenes change, and never read back from the records after the extension's own writes. It holds references to datablocks, never to data inside one, and checks each before returning it, so no lookup returns a removed datablock: a removed datablock's check rereads the one manifest that names it, and a removed scene or destination rebuilds the cache, which then answers again. Bindings are keyed by binding identity, and claims by Blender's `session_uid`, which no other datablock in the session gets: a new datablock often takes a removed one's address. Chosen because no persistent identifier finds a datablock without a scan (names change on rename, and Blender has no lookup by `session_uid`), so a cache holding no references would scan `bpy.data` on every hit, which M7's selection mapping can't afford. Rejected: a generation counter that makes stale lookups fail, since the checks answer them from current data instead. Data inside a datablock is never held: a modifier held across undo read freed memory (one check, [M3 plan](plans/M03-bindings.md), D8). See [Undo and Runtime State](spec/lifecycle.md#undo-and-runtime-state). | `F-BINDING-STATE` |

| Ownership metadata format | M3 | **Chosen (with the user, 2026-10-19):** each binding has a **manifest**, a record on its destination collection with one entry per managed resource, keyed by resource identity. An entry names the resource's datablock (an ID pointer), the source entities it covers (composed-stage paths), its representation role (M5's vocabulary), and the managed resources it uses. Ownership is which binding's manifest holds the entry. Managed dependents are derived by inverting the uses, and unmanaged users are read from Blender's user graph when an operation needs them, since nothing persistent can track them. Nothing is stored on the managed datablocks: a datablock is managed by the binding whose manifest names it, so a duplicate or appended copy of managed content is unmanaged with nothing to reconcile, and content two manifests name is ambiguous. Chosen because ownership tags on every datablock duplicated what the manifest records: on 10,000 objects each record kind added about 1.1 MB to the `.blend`, and reading the whole manifest through the record framework took 32 ms (one ad hoc run, macOS), so hot paths use runtime indexes built from it (M3 Phase D). Rejected: a tag on each datablock as well, which copying duplicates. See [Ownership and Lifecycle](spec/lifecycle.md#ownership-and-lifecycle). | `F-OWNERSHIP-AMBIGUITY` |
| Manifest writes: whole and per entry | M3 | **Chosen (with the user, 2026-10-20):** a manifest is written whole (`runtime.set_manifest`), for a binding's first publication and Phase 1's full rebuilds, or by entry (`runtime.set_manifest_entries(binding_id, changed, removed)`), for Phase 2 refreshes that change some resources. An update is checked as a whole manifest is before anything is written: uses resolve, no remaining entry uses a removed resource, and no datablock is named twice, found through the ownership index rather than a scan. Only its entries are written, staged so a value or key ID properties can't hold changes nothing; a record at an older version is written whole. The ownership index changes only those entries' claims, and an empty update writes nothing, as a no-op refresh must ([Affected Content](spec/incremental.md#affected-content)). Chosen because a whole write pays for every entry: publishing a one-resource change to a 10,000-entry manifest took 51–68 ms whole and 0.7–1.1 ms as an update, 0.02–0.05 ms at 100 entries (bpy wheel, 5 runs each); what's left is copying the entries in memory and, for removals, a scan of the uses. Not measured: the undo memory a step keeps for a changed manifest, which no Python API reports; an undo push took 10–22 ms on 10,000 objects whatever changed. Rejected: updates alone, where a full rebuild would name every old resource as removed. | UV-set names | M4 / M8 | **Chosen (with the user, 2026-10-27):** a UV set is a `texCoord2f[]` primvar, as USD types it. A binding's requested settings gain **UV-set names** beside its payload policy: a list of globs, matched case-insensitively against a whole primvar name, that also make a UV set of a `float2[]` primvar with vertex, varying, or faceVarying interpolation. The default is an empty list, which keeps USD's typing. Chosen because production assets author untyped UVs: ALab has `st` as `float2[]` on 308 meshes ([M4 plan](plans/M04-prototypes.md), A3), which USD's typing alone would show without their textures' UV sets; a list lets a pipeline name its own conventions, and the interpolation rule keeps a matching constant or uniform value out.
