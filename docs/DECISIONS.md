# Decision Register

Milestones update this register when they settle a decision. Every in-scope requirement is traced in the requirement-to-test matrix created in M1, with high-risk entries marked separately by M4. Settled contract decisions update their requirement rows and test/oracle coverage before implementation. Fixture IDs refer to [Named Contract Fixtures](testing/strategy.md#named-contract-fixtures).

| Synchronization API | M3 | **Chosen (with the user, 2026-10-16):** callers reach a binding through an immutable handle that holds only its persistent identifier, never a datablock or cached state, so undo, redo, and file loads can't leave it stale (UNDO-07); a handle whose binding is gone raises for methods that need records; release remains valid. `handle.synchronize(time_code=None)` synchronizes at the time code it is given, or without one at the target scene's current frame's, and `handle.cache(time_codes)` caches other time codes in the published generation (row "Time-sampled data representation", 2026-11-02); the default time code isn't a frame to key, so passing it to `cache` is misuse and raises (M5 E1, with the user, 2026-11-06). The time code is the attempt's, not a stored setting (with the user, 2026-10-19): callers derive it at each synchronization, so a binding's configuration holds only the requested settings, which change only through `handle.set_settings(...)` and don't synchronize. The last attempt and the published generation record the time code they used. Synchronizing returns an immutable result with the result state and diagnostics; expected failures are results, and exceptions report only misuse and defects, such as a failed write to the pending-cleanup ledger once the operation has found it readable (with the user, 2026-11-06). A failed publication write stays a fatal diagnostic: publication undoes itself, while a ledger write that fails leaves leftovers nothing could report. Creating bindings, finding a scene's bindings, and reporting copied bindings belong to the process's bindings. Attaching and releasing belong to each handle. Methods delegate to functions keyed by identifier, which tests exercise. `handle.reload(layers=None)` rereads source layers on request without synchronizing (row "Dirty layers and reloading", 2026-10-18). `handle.retry_cleanup()` retries the cleanup earlier attempts left pending, explicitly and without USD access; M11's cleanup builds on it (M5 D9). `handle.possibly_out_of_date()` says whether the display may not show the source as it is now, as after an undo restores an earlier generation (M5 D12, row "Undo step for a published synchronization"). M3 settled the module and names: `proscenium.api.bindings`, whose `BINDINGS` is the process's `Bindings`. **The result's fields (M5, with the user, 2026-11-03):** the result state; the operation's own deduplicated diagnostics, with a pending-cleanup diagnostic for each resource it left pending; the time codes it attempted; and the binding's current cleanup status, apart from its own diagnostics (DIAG-06). The state derives from the operation's own diagnostics, so cleanup an earlier attempt left pending doesn't keep a later synchronization from succeeding. A diagnostic holds a stable code naming its problem (such as `untranslated-type`), which gives it one category and one severity (M5 C1, with the user, 2026-11-04), and its message, binding, source path, property path, asset, fallback, the layers it concerns, and for pending cleanup its resource's ledger key and role, so callers and tests identify it without reading its message. **Non-reentrancy (M5, with the user, 2026-11-03):** while a synchronization or `cache` call is running, `synchronize`, `cache`, `attach`, `release`, and `reload` on any binding raise before changing anything; `set_settings` is allowed, and the running attempt keeps the settings it started with. A cleanup retry is exclusive the same way, and `retry_cleanup` is among the calls that raise (M5 D11, with the user, 2026-11-06), since a retry removes datablocks and writes the ledger, and one during a synchronization would remove that attempt's prepared work. Process-wide, since every binding shares the file's ledger, the undo step a publication pushes, and the bindings' runtime state. The GIL doesn't prevent a nested call: one can come on the same thread from a Blender handler or a USD notice the transaction triggers, or from another thread while the core captures without the GIL. A flag that `Bindings` holds suffices, since only code holding the GIL reads or writes it. See [Synchronization API](spec/source-access.md#synchronization-api). | M3 and M5 API tests |
| Binding records read when called | M3 / M5 | **Chosen (with the user, 2026-11-06): no runtime cache of the bindings' records.** Every lookup reads the records as they are when it's called: a binding's configuration from the collections holding binding records, the binding index, its manifest from its destination, and the pending-cleanup ledger from the index's Text. Ownership of a datablock is answered from its users (`bpy.data.user_map`), a manifest's pointer being one: the manifests of the collections among them are read, so a query reads only the manifests that name the datablock. Nothing holds a datablock reference across operator calls, so file loads, undo, redo, and removals need no handler and no check of held references: a removed datablock's pointer is cleared in the records, and a lookup never sees it.
