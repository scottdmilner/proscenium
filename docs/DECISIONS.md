# Decision Register

Milestones update this register when they settle a decision. Every in-scope requirement is traced in the requirement-to-test matrix created in M1, with high-risk entries marked separately by M4. Settled contract decisions update their requirement rows and test/oracle coverage before implementation. Fixture IDs refer to [Named Contract Fixtures](testing/strategy.md#named-contract-fixtures).

| Dirty contributing layers on file-backed refresh | M3 | **Chosen:** fail with a source-access conflict naming the layers. The contributing layers are the non-anonymous layers the binding's stage composes under its payload policy, so a dirty layer reached only through an unloaded payload, which can't change the display, doesn't conflict (settled with the user, 2026-10-15). Rejected: evaluating in-process state with a divergence diagnostic. May upgrade to a private disk view if one is found that is cheap enough (M1: feasible but slow). | `F-DIRTY-LAYER` |
| Private disk view feasibility | M1 | **Settled:** feasible in correctness but too slow as built. Anonymous copies of every reachable layer, with remapped asset paths, matched disk on the probe scene. On ALab it gave the same prim paths and type names as a normal open (values not compared), but took 16–17 s against 0.5–0.7 s for a normal open (warm cache). Relocating the scene (copy or symlink) leaks through absolute-path references. Untested: resolver search paths, asset-path expressions, clips, `.usdz`, and lazy copying. Keep the conflict failure unless M3 finds a cheaper view. See the [feasibility record](feasibility/runtime-record.md#private-disk-view). | M1 feasibility record |
| Strictness of the file-backed refresh contract | M3 | **Chosen (with the user, 2026-10-15): each file-backed binding keeps and reuses its own stage.** The binding opens its stage outside every USD stage cache and never shares it with other bindings or tools. Refresh reloads the clean contributing layers that changed on disk, so the result matches a stage newly opened from the same files, and still fails on dirty contributing layers (row "Dirty contributing layers on file-backed refresh"). The binding stage's anonymous layers (its session layer and those beneath it) compose into the display, so a future editor can show unsaved edits through the live stage without saving to disk; synchronization never authors them, and they are not saved in the `.blend`. This stage is the binding's live stage; callers get it from the binding, which never places it in a stage cache. Chosen because a new stage per refresh pays the open and the Hydra chain's construction again (0.58 s and 0.41 s on ALab, [record](feasibility/runtime-record.md#measurements-m1b-phase-e)) and resets the scene-index population, losing the notices Phase 2 can use (M13). **Risk:** a non-forced reload misses a rewrite within the same second on Windows ([record](feasibility/runtime-record.md#dirty-layers-and-fresh-stages)); M3 Phase C settles the change check, tested by comparing a reused stage with a newly opened one. See [File-Backed Refresh](spec/source-access.md#file-backed-refresh). | M3 decision record; `F-DIRTY-LAYER`, `F-CACHED-STAGE` |
| Stage-level state reproduced for in-memory sources | M3 | **Chosen (M3):** a private stage per binding over the caller's root and session layers, opened outside every stage cache with the caller's resolver context. The layers are shared, so the caller's unsaved edits and session-layer opinions are seen live. At each synchronization the private stage's population mask, muted layers, and interpolation match the caller's; the binding's payload policy replaces the caller's load rules; the edit target doesn't affect composition and isn't reproduced. M1 found this reproduces the caller's composed values and leaves the caller's stage unchanged, with the default resolver only ([record](feasibility/runtime-record.md#in-memory-source-candidates)). See [In-Memory Sources](spec/source-access.md#in-memory-sources). | `F-PRIVATE-STAGE` |
| In-memory source key contract | M3 | **Chosen (with the user, 2026-10-16):** a caller-chosen source key names one in-memory source within a `.blend`; several bindings may share it, and attaching a stage under a key attaches it to all of them, so bindings with different payload policies on one stage need one attach call. Reattachment requires an exact key match. The stored root-layer identifier is informative only, since an anonymous or unsaved source's identifier does not survive the session; attaching a stage whose identifier differs from it requires explicit confirmation. Replacing the stage preserves stored source selections. See [Source Identity](spec/source-access.md#source-identity). | M3 reattachment tests |
| Synchronization API | M3 | **Chosen (with the user, 2026-10-16):** callers reach a binding through an immutable handle that holds only its persistent identifier, never a datablock or cached state, so undo, redo, and file loads can't leave it stale (UNDO-07); a handle whose binding is gone raises when used. `handle.synchronize(time_code)` records the time code as the requested time code; the other requested settings change only through `handle.set_settings(...)`, which doesn't synchronize. Synchronizing returns an immutable result with the result state and diagnostics; expected failures are results, and exceptions report only misuse. Creating bindings, finding a scene's bindings, and attaching under a source key span bindings, so they are module functions. Methods delegate to functions keyed by identifier, which tests exercise. Names, module, and result fields are settled with the implementation (M3 Phase C, M5). See [Synchronization API](spec/source-access.md#synchronization-api). | M3 and M5 API tests |
| Copied bindings | M3 | **Chosen:** disabled pending repair. Canonical-candidate rule open. Rejected: automatic new identity; treat as detached. | `F-OWNERSHIP-AMBIGUITY` |
| Browsing universe and inspection metadata set | M2 / M4 | **Draft (M2, with the user, 2026-10-15)**, finalized by M4. **Callers have the live stage** and browse and inspect it through the USD API, so there is no inspection metadata set and no browsing function. **Two layers:** a persisted correspondence layer, produced by synchronization, resolves picks, says which prims are displayed, and shows selections, storing no inspection data; an inspection layer maps picked prims to selection targets by kind on the live stage (row "Inspection layer"). The browsing universe is displayed content only: prims outside instance contents that display in the viewport, or have displayed descendants, plus their ancestors, derived from correspondence. Instance-proxy descendants, unloaded payloads, inactive and abstract prims, and composition provenance are left to a Phase 3 scene-graph inspector. Hierarchy and kinds come from the composed stage, never Hydra. Selection targets are chosen at a caller-supplied level (prim or model kind), never inside an instance, and select their subtree. Source selection is mirrored into Blender selection, and Blender selection produces source selection; native tools or an extension tool is open for M4. Without a live stage nothing interaction-related works: the saved display is plain content, and stored selections are kept. Framing is not provided. See the [Interaction Contract](spec/interaction-contract.md) and the [M2 plan](plans/M02-contracts.md). | M2 interaction fixtures and oracle; M4 checks and finalization |
| Inspection layer | M2 / M7 | **Chosen (with the user, 2026-10-15):** a C++ library that maps picked prims to selection targets by model kind on the live stage. It does not touch Blender and does not depend on the compiled core: no shared code, and no use of its scene indices, snapshot, or plan. The core calls it and exposes the interaction functions through its own bindings, routing to the correspondence and inspection layers internally, so paths never pass through Python between them; the only Python in interaction updates Blender's selection. It is read-only. Everything else about the source, callers read from the live stage through the USD API. Chosen because a kind-level selection runs correspondence, then this layer, then correspondence again, and a Python step in the middle would be GIL-bound per-path work between compiled calls. No measurement has been taken (M4 measures selection at scale). A file-backed binding's live stage is its own stage, which it reuses across refreshes; an in-memory binding's is the caller's (M3, row "Strictness of the file-backed refresh contract"). See [Two Layers and the Live Stage](spec/interaction-contract.md#two-layers-and-the-live-stage). | M7 inspection tests; M4 measurements |

| Native core distribution | M1b | **Chosen (with the user, 2026-10-14): GitHub releases**, one extension zip per platform and Blender minor version, which users install from disk. Not listed on extensions.blender.org, so its rule against compiled code (Terms of Service §3.6) doesn't apply; a rebuild and new release for each Blender minor version that changes USD is acceptable (settled 2026-10-09). Blender's dependency headers are pinned per Blender release. Not chosen: a self-hosted extension repository, or both. **Risk:** the module binds to Blender's exact USD build (namespace `pxrBlender_v26_03__pxrReserved__`), so each zip supports only its Blender minor version: `tools/build_extension.py` sets `blender_version_max` to the next minor (M3). Untested: a download through a release page (macOS quarantine), and updating or uninstalling while the module is loaded. See the [record](feasibility/runtime-record.md#distribution-m1b-phase-f). | M1b distribution check (`tools/feasibility/hydra_bridge/distribution.py`), all three platforms |
| Time-sampled data representation | M1b / M4 | Open. Treating time codes as frames and authoring animation data is permitted ([Transforms and Time Codes](spec/support/transforms.md#transforms-and-time-codes)) but not preferred. **M1b findings** ([record](feasibility/runtime-record.md#for-m4-evaluating-frames)): the core evaluates one time code per capture, and caching several frames is a layer above capture. Capture matches USD at each time, and a time change dirties exactly the varying values (equal samples included), so successive captures say what changed. Direct USD (`ValueMightBeTimeVarying`, `GetTimeSamplesInInterval`) gives authored keys when a representation needs them. Hydra's interval query is a motion-blur API and isn't needed. M4 compares per-time-code snapshots against animation-data representations: keyframed transforms, mesh cache modifiers, and **Geometry Nodes baking**, which is expected to perform better at the cost of higher memory use (to be measured). M4 records the time-code-to-frame mapping for any it adopts. Mesh cache modifiers that read the USD file must first reconcile the application-boundary, in-memory-source, offline-reopening, and pre-mutation-diagnostics requirements listed in [M1b](milestones/M01b-evaluation-gate.md). | M1b feasibility record; M4 prototypes and measurements |
