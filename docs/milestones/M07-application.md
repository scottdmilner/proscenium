# M7 — Blender application and source inspection UI

**Implements:** [Blender Application](../spec/pipeline.md#blender-application), the inspection and interaction behavior in [Source Inspection and Interaction](../spec/interaction.md#source-inspection-and-interaction), except correspondence through batching (M8) and instance-root selection (M10), the application side of [Coordinate Conversion](../spec/support/transforms.md#coordinate-conversion), exposing model kind and asset metadata in [Models and Unsupported Content](../spec/support/visibility.md#models-and-unsupported-content), display-correspondence persistence in [Persistence](../spec/lifecycle.md#persistence), stale-content retirement and external-usage protection in [Ownership and Lifecycle](../spec/lifecycle.md#ownership-and-lifecycle), and the display of cached time codes in [Cached Time Codes](../spec/pipeline.md#cached-time-codes) and [Transforms and Time Codes](../spec/support/transforms.md#transforms-and-time-codes), as M4's decision represents them (row "Time-sampled data representation"), except time-varying topology (M8); and incremental refresh, Phase 1's since 2026-11-07 (DECISIONS.md "Partition unit"): [Change Discovery](../spec/incremental.md#change-discovery) and [Affected Content](../spec/incremental.md#affected-content), except external assets changed without a USD edit (M9), managed-display repair (M11), and the churn budgets (M13), the incremental guarantees in [Synchronization Transaction](../spec/pipeline.md#synchronization-transaction), and the [Incremental Synchronization Tests](../testing/strategy.md#incremental-synchronization-tests). M8 to M11 make their own content incremental as they build it.

**Depends on:** M4 (partitioning decision and finalized interaction contract), M5 (application-layer interface, transaction, and stub tests), M6 (display plans).

**Scope limits:** repair of user-modified content is M11 work.

**Decisions and deliverables:**

- The real application layer for the chosen representation, connected to M5's ownership tracking, transaction, and publishing. It replaces the stub's `prepare` and `key_time_codes` (`synchronization/application.py`): each datablock is held in `PreparationResources` with `track` as soon as it's made, before anything else can fail (TXN-08), and each change a cache call makes to a published resource has its undo appended to `PreparationResources.undo` before it's made (CACHE-03).
- Object names that land at the end of Blender's sorted lists (DECISIONS.md "Managed object names"): M7's application layer names every object it creates, and each copy's own data, `~<generation>.<ordinal> <prim name>`, as M6's stub does. They matter most when synchronizing again, beside the display being replaced: with prim names, the stub prepared `updates-10000` the second time in 78.3 s, against 3.0 s with these ([M6 plan](../plans/M06-evaluation.md), C7). M7 sets hide flags together, as the stub does, since setting one runs an update that resyncs every collection.
- The plan M6 gives application, which the stub applies ([M6 plan](../plans/M06-evaluation.md), C1, C2, C4, C5, C8, D4):
  - Drawn copies, one per correspondence entry in source order, with their content in the copy table's read-only buffers: `copy_worlds` in Blender's layout, which `foreach_set("matrix_world", ...)` takes as it is, `copy_objects`, `copy_geometries`, `copy_placeholders`, `copy_viewport`, `copy_render`, and `copy_shears`. A copy's resources are an `object` and, for a mesh, a bounds mesh of its provisional geometry description, which M8 replaces with mesh content.
  - Shear parents: a sheared copy's partition has a `shear parent`, which its object uses; `shear_parent_worlds` and `shear_object_bases` hold the split, and `copy_worlds` the whole world transform. The stub makes the parent an unselectable empty and keys an object's basis below it. A shear that changes over time is M7's; a batched copy needs no parent, since its instance's matrix holds the shear.
  - Placeholders and markers: a gprim the core doesn't translate is a box of its usable bounds, or with none an empty marker, whose object holds no data, each with its `untranslated-type` diagnostic.
  - Destinations: an invisible copy stays in the plan, shown in neither destination, and its hide flags come from `copy_viewport` and `copy_render`; a copy whose purpose neither destination includes isn't in the plan.
  - Batch groups: `Plan.batch_groups(minimum)` groups the copies a batch shows. The plan's resources stay an object per copy, and M7 makes batch partitions from the groups (ROLE-04).
  - Reading it ([record](../feasibility/runtime-record.md#reading-the-plan-m6-phase-f)): each copy's object index took 9 ns from its buffer and 220 ns from the correspondence tuple, and every field of the tuples about 4.5 µs a copy at 30,001 copies, so the integers in correspondence entries and resources could cross as buffers too, with paths staying tuples.
- What a full rebuild costs beside its display ([M5 plan](../plans/M05-architecture.md), F1, F2): its undo step holds about the display's size, 1.2 GB on ALab, and its retirement about the datablocks removed times those left in the file, 5.0 s on ALab. Incremental refresh keeps unchanged datablocks, which shrinks both: a step after moving one object held 4.5 MB.
- Retirement after an undo push (with the user, 2026-11-09, from M6's F5; [record](../feasibility/runtime-record.md#retiring-a-large-display-m6-phase-f)): once an undo step has been pushed, as with a window after each synchronization, the view layer has a base for each published object. Publication unlinks the obsolete objects, but their bases stay until the next depsgraph update, and `bpy.data.user_map` names the Scene their user through them, so `removal.remove_unused` releases the whole obsolete display, leaving it in the file unmanaged, and the synchronization succeeds. Updating each scene's view layers before reading users removed it in M6's ad hoc check, at the cost of a depsgraph update (0.3 to 0.6 s on ALab, 1.9 to 3.8 s at 30,001 objects); M7 decides the fix. Removing for real costs 3.3 to 3.7 s on ALab and about two minutes at 30,001 objects while their replacements are in the file, with global undo on or off.
- Incremental refresh (with the user, 2026-11-07), as the bridge's updates did: each synchronization captures and plans, compares the plan with the published generation's, and replaces only the partitions whose planned content changed, keeping the rest and their Blender identities and selections, then retires what no partition names, deleting only obsolete resources that are safe to remove under the ownership and external-usage rules. A first synchronization, or an explicit full rebuild, builds every partition.
  - A change matrix enumerating Change Discovery's cases, a mapping from source-affected entities to dependency-affected and replacement-affected display resources for M7's content, which M8 to M11 extend for theirs, and a decision on when local updates, partition rebuilds, or explicit full rebuilds are appropriate.
  - Scene-index observer notices (M1b adopted Hydra) as one discovery source, within the limits in the [incremental design note](../spec/incremental.md#change-discovery), with recovery from missed or coalesced notices, and a validated in-memory-stage interface for callers whose edits a refresh discovers.
  - The application side as the bridge built and measured it ([M4 plan](../plans/M04-prototypes.md), C1, C2; the bridge's `plan_diff`, `update.py`, and `batch_update.py` in [its sources](../../tools/feasibility/hydra_bridge/src/README.md)): the plan diff, ported into the core, matches meshes by content hash and byte comparison, materials by everything the plan holds, and objects by identity, and lists changed, repointable (only mesh or materials differ), moved, and removed objects. It took 38 ms on ALab in the bpy wheel but 76–123 ms inside updates in the binary, and planning 0.33–0.43 s inside updates against 0.25 s alone, not investigated; together they were most of every small update ([record](../feasibility/runtime-record.md#measurements-m4-phase-c)).
  - What depends on time, from Hydra's dirtying, for `cache` to key only what varies ([M4 plan](../plans/M04-prototypes.md), E3; with the user, 2026-11-08, from M6's C9, since it shares incremental capture's machinery): an observer on the chain records Hydra's notices between captures into the snapshot; a capture that forces its time dependencies (`SetTime`'s `forceDirtyingTimeDeps`, and the source-info filter's own) records the locators they dirty, which planning maps to each copy's varying aspects through its prim, subsets, instance roots or point instancer, and, for purpose visibility, which Hydra doesn't flatten, their ancestors; it predicted every varying copy on ALab. Forcing makes Hydra's flattening forget the values it dirties, so the forced notices are requeued for the next capture (the bridge's `capture.cpp`). The source-info filter gains the bridge's stage listener, which dirties what Hydra misses, such as a computed extent when the points or widths it follows change, which Hydra dirties only as primvars. A suggestion: the frames a cache call adds confirm what varies, and nothing fails on a misprediction.
  - Incremental capture, as the bridge's capture did ([M1b plan](../plans/M01b-evaluation-gate.md#phase-c-log); its `capture`, `scene_index_graph`, and source-info filter): re-copy only the prims notices named since the previous capture (added and dirtied exactly, removed and renamed by subtree), sharing the others' retained containers, which never change, so earlier snapshots stay intact. On 23 edit steps it equaled full captures record by record, on one scene; that isn't proof notices are complete. `HdsiComputeSceneIndexDiffDelta` compares handles, not values, so its oracle is a full re-read.
  - What M6's snapshot gives it ([M6 plan](../plans/M06-evaluation.md), B1; [record](../feasibility/runtime-record.md#capture-and-planning-m6-phase-f)): a retained scene index of each prim's `HdMakeStaticCopy` of the schemas planning reads, opaque to Python, so a capture can share an earlier snapshot's containers for the prims no notice names. M6 builds a chain per call, and on ALab building it is 0.31 s of capture and planning's 0.43 to 0.49 s, nearly all UsdImaging's native-instance aggregation; a chain kept between synchronizations, which the observer needs anyway, pays it once. Its owner releases it when the binding detaches, changes payload policy, reloads, or is disposed of, so a released stage expires (SRC-02); a release drops the stage scene index without `SetStage(nullptr)`, 0.03 s against 0.4 s on ALab.
  - The bridge's chain ends in `HdsiPrimTypeNoticeBatchingSceneIndex`, which the core's chain doesn't have: the scene is empty until its first `Flush()`, notices wait for each one, and capture flushes every time. One priority for every prim type suits re-reading; materials first might suit applying notices, untested ([M1b plan](../plans/M01b-evaluation-gate.md#phase-b-log)).
  - `SetTime` dirties exactly the locators flagged time-varying, and only on data sources already pulled; flags are never cleared, so dirties also arrive for removed paths and unchanged values ([M1b plan](../plans/M01b-evaluation-gate.md#change-tracking-and-time)). Hydra never flags mesh orientation, scheme, doubleSided, subdivision tags, or subset indices (M8).
  - The source-info filter rebuilds more than needed on a time change: 16 containers on the bridge's animation scene, where an ad hoc build that invalidated only for extents rebuilt 3 ([M1b plan](../plans/M01b-evaluation-gate.md#phase-d-log)).
  - Manifest updates by entry: an update copies the manifest's entries and, with removals, scans every entry's uses ([M3 plan](../plans/M03-bindings.md), D8), and reads the manifest unless its caller passes the one it read (`published`, [M5 plan](../plans/M05-architecture.md), F3). If that's too slow, a count of each resource's users and a persistent map in place of the copied entries would make an update cost only what it changes.
- The source inspector, and the agreed browsing, selection, and highlighting behavior from the finalized interaction contract.
- A binding panel that lists a scene's bindings once per draw, measured against M4's interaction budgets: a listing reads every collection's binding records, 13 µs with one binding (DECISIONS.md "Binding records read when called").
- From M4's selection tool ([M4 plan](../plans/M04-prototypes.md), F2, F3): whatever owns the destination's display, not a selection tool, decides when managed content is selectable (the destination collection's `hide_select`, 44 ms on ALab against 0.95 s per object) and which overlays the 3D views hide, as later tools may need it selectable; the active tool's changes come from message-bus subscriptions to `WorkSpace.tools` and `Window.workspace`. A file saved while Source Select is active keeps those settings, so loading restores or ignores them. Blender's own outlines stay the default; outlines of the extension's own would need a C-level draw engine to reuse Blender's GPU geometry and dim what is hidden. A box selects elements by their world bounds' centers, since many copies hold their placement in their points.
- Cached time codes for every variation (CACHE-10), with mechanisms suggested and not probed ([M4 plan](../plans/M04-prototypes.md), F5): a copy's materials chosen by a keyed index (a Geometry Nodes Set Material fed by an Index Switch), or an object per material state with keyed visibility; a placeholder's bounds box and empty marker both made, each with keyed visibility; and a property keyed, where its primvar is blocked, with its reader's fallback (M9). A batch has an object per selection state its instances hold (D14).
- The inspection layer of the [interaction contract](../spec/interaction-contract.md#two-layers-and-the-live-stage): a C++ library that maps picked prims to selection targets by kind on the live stage, independent of the compiled core and of Blender, which the core calls and exposes through its bindings. It reads the live stage M3 defines for each binding. It follows the core's type-identity rule, and registers any Tf-factory type through an exported USD helper, as Hf's plugin registry does, never by deriving from a header-only factory base: a keyless UsdImaging adapter built that way failed on macOS with "Cannot manufacture type" ([M1b plan](../plans/M01b-evaluation-gate.md#phase-c-log)).
- Selection maps back through the plan's correspondence, never through `HdxPrimOriginInfo`, which is quadratic in the instance count in Blender's USD (v26.03): 1,330 ms against 25 ms at 50,000 objects ([M1b plan](../plans/M01b-evaluation-gate.md#phase-b-log)). A plan index names an element within one generation only, so a pick held across a republish needs the element's resource identity ([M4 plan](../plans/M04-prototypes.md), B3).
- From the bridge's application path:
  - A moved object that fails to publish is restored from the location, rotation, and scale Blender stored, not from its old matrix, which can decompose under another sign convention ([M4 plan](../plans/M04-prototypes.md), E2).
  - Every object of a cached mesh gets its frames modifier when the mesh is written ([M4 plan](../plans/M04-prototypes.md), E5). The modifier goes first in the stack, ahead of a carrier's batch modifier, and a FLOAT2 sample is stored as a 3D vector, since a 2D vector on corners becomes a UV map (the bridge's `keyframes.py` and `attribute_samples.py`).
  - Indexing a Vt array from Python costs about 48 µs a record, about 0.34 s of the object baseline's construction on ALab, so application reads converted values ([M4 plan](../plans/M04-prototypes.md), D5).
- Memory measured with the depsgraph's evaluated copies in mind: they hold their memory until its next evaluation, 1.7 GB after deleting the importer's ALab data ([M1b plan](../plans/M01b-evaluation-gate.md#phase-e-log)).

**Tests:**

- Resulting Blender content and source correspondence for hand-constructed plans.
- Repeated application: several unchanged synchronizations follow [Resource Stability](../spec/lifecycle.md#resource-stability), with stable active counts, stable total managed counts when disposal succeeds, separately tracked leftovers during disposal failure, and count recovery after explicit cleanup.
- Incremental refresh, for each change-matrix case M7's content covers: the display then holds what a clean full rebuild does, the affected-resource sets are the expected ones, unaffected content keeps its identities and isn't rewritten, and selections whose identities remain valid survive; repeated edits, inherited changes, and repartitioning; old and new dependencies when structure changes; missed or coalesced notices; `F-NO-OP-REFRESH` with zero unnecessary writes, and `F-SAME-VALUES`.
- Retirement after an undo push: synchronizing again after the API pushed its undo step, as with a window, removes the obsolete display; tests in background mode push none unless they patch it on.
- The M5 failure-injection tests, rerun unchanged against the real application layer.
- Application-time resource failures abort the transaction unless the plan authorized a fallback.
- `F-UNMANAGED-USER`.
- `F-OFFLINE`: correspondence records unchanged through reopening with the source unavailable (REOPEN-07).
- The M4 interaction checks against the real display: `F-KIND-HIERARCHY`, `F-NESTED-SELECTION`, `F-UNIVERSE-MEMBERSHIP`.
- Model kind and `assetInfo` read from a binding's live stage on `F-KIND-HIERARCHY` (MODEL-01).
- End-to-end tests using M6-generated plans.
- M6's tests of the stub, updated for the real application layer ([M6 plan](../plans/M06-evaluation.md), D4, E2):
  - `blender/test_application.py` checks what the stub draws: each copy an object with `display_type` `BOUNDS` and a bounds mesh of its extent's eight corners, an empty marker holding no data, a sheared copy under an unselectable shear parent, hide flags, and managed names. Each check moves to what the real layer makes of the same plan.
  - `blender/test_time_varying.py` checks a cache call's participation on its plans alone, since the stub keys only transforms; once M7 keys visibility, it also checks Blinking's hide flags in Blender at each cached time code. It reads a sheared copy's world transform through its shear parent and a copy's object by its manifest entry, as the stub makes them.
  - `blender/test_planning_inputs.py` reads each copy's placement and hide flags from the stub's objects.
- Cached time codes: synchronized at one sampled time code and cached at the others in more than one order, each frame displays what a clean synchronization at its time code does, whether they were cached in one call or several, and a frame between them the latest before it, with interaction answering for that time code; the display caches nothing on its own (CACHE-01, CACHE-08, CACHE-09, CACHE-10, XFORM-11, XFORM-13, XFORM-14).

**Exit condition:** the application layer displays and inspects plans, refreshes incrementally with results equal to clean rebuilds for its change-matrix cases, passes the M5 failure-injection suite and `F-UNMANAGED-USER`, and meets the boundary rule in Blender Application.
